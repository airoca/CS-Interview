- **Race Condition과 Critical Section이 무엇이고, 경쟁상태를 막기 위해 어떤 방법을 사용하는지 설명해주세요.**
    
    두 개 이상의 스레드가 공유자원에 대해 접근하려고 서로 경쟁하는 것을 Race Condition(경쟁상태)라고 한다.
    
    이 공유자원이 존재하는 구간으로 Race Condition이 일어날 수 있는 영역을 Critical Section(임계영역)이라고 한다.
    
    이러한 임계영역에 대한 경쟁상태를 제거하기 위해서 한 공유 자원에 대해서 한 스레드에만 접근을 허락하도록 하는 상호 배제(Mutual Exclusion)를 사용한다.
    

- **Critical Section의 문제 해결을 위한 조건을 설명해주세요.**
    - **Mutual Exclusion (상호 배제)**
        - 한 번에 하나의 프로세스/쓰레드만 임계 구역에 들어갈 수 있어야 한다.
    - **Progress (진행)**
        - 임계 구역에 아무도 없을 경우, 대기 중인 프로세스 중 일부가 반드시 진입할 수 있도록 보장되어야 한다. (작업이 진행 중이어야 한다.)
    - **Bounded Waiting (한정된 대기)**
        - 어떤 프로세스도 무한히 기다리지 않고, 언젠가는 임계 구역에 들어갈 수 있어야 한다.

- **Lock과 Mutex에 대해 설명해주세요.**
    - **Lock**
        - 임계 구역(Critical Section)을 보호하기 위한 동기화 메커니즘 전반을 의미한다.
    - **Mutex (Mutual Exclusion)**
        - 오직 하나의 쓰레드만 자원을 사용할 수 있도록 보장하는 락의 종류이다.
        - Mutual Exclusion의 줄임말이지만, 해당 개념 자체가 아니라, “Mutual Exclusion을 보장하기 위한 구체적 도구인 Mutex” 라고 봐야한다.
        - 세마포어, ReentrantLock, Read/Write Lock, Spinlock 등은 개념적으로는 모두 Mutual Exclusion을 구현할 수 있지만, 'Mutex'라는 용어는 그들 중 특정한 구현체(보통 OS 레벨의 Binary Lock)를 가리킨다.

- **모니터에 대해 설명해주세요.**
    - 모니터(Monitor)는 동시성 제어를 위한 고수준 추상화 개념이다.
    - 락(mutex), condition variable, 임계 구역 등 다양한 동기화 도구들을 하나의 구조체처럼 묶어 캡슐화한 개념이다.
    - Java의 `synchronized` 키워드는 메서드 전체를 ****보호하는, 모니터 개념을 적용한 대표적인 방식이다.

- **주요 Atomic 하드웨어 명령어를 소개해주세요.**
    - **Test And Set**
        - 0은 락 해제 상태, 1은 락 점유 상태
        - 현재 flag가 1인 경우 Lock을 (무의미하게) 1로 Set 한 후 1을 리턴하여 Spin
        - 현재 flag가  0인 경우 Lock을 1로 Set 한 후 0을 리턴하여 while 문 탈출
    - **Compare And Swap**
        - flag 값을 확인하여 0과 비교
        - 일치할 경우, flag의 주소에 1을 저장하고, 0을 리턴
        - 반대로, 일치하지 않을 경우, 1을 리턴하여 Spin

- **단순히 `yield()` 방식으로 Spinning을 해결할 수 없는 이유는 무엇인가요?**
    - 단순히 OS의 시스템 콜을 통해 현재 실행 중인 스레드를 Running 상태에서 Ready 상태로 바꾸는 것이다.
    - yield 방식에서는 Lock을 획득하지 못할 때마다 `yield()`를 통해 즉시 컨텍스트 스위칭이 발생하고, 해당 스레드는 Ready 상태로 전환되는데, 해당 스레드가 다시 스케줄링되어 또다시 Lock을 획득하지 못할 경우, 다시 `yield()`를 통해 컨텍스트 스위칭이 발생하는 과정이 반복된다.
    - 하지만 큐(스레드를 재우는) 방식의 경우, Lock을 획득하지 못한 스레드를 재운 후, Lock이 풀렸을 시점에만 unpark()를 통해 해당 스레드를 깨우므로, 불필요한 컨텍스트 스위칭이 발생하지 않는다. 공정성 차원에서 또한 큐를 사용한다는 점에서 순서를 보장한다는 것을 쉽게 이해할 수 있다.

- **대기 큐를 사용하여 Spinning을 해결하는 방법을 요약해주세요.**
    - **park()**
        - 해당 System Call을 호출한 스레드를 재우는 함수이다.
    - **unpark(threadID)**
        - threadID로 지정된 스레드를 깨우는 함수이다.
    - **flag**
        - Lock의 상태를 표현한다.
    - **guard**
        - Lock의 상태를 변경하는 코드의 원자성을 보장하기 위해 사용된다.
        - guard를 얻기 위한, “OS 레벨의” 짧은 Spinning이 요구된다.
        - 왜 짧은 Spinning일까? 작업의 완료를 기다리는 Spinning이 아니라 Lock의 상태를 확인하기 위한 Spinning이기 때문이다.
        - Lock의 상태가 1인 경우, 해당 스레드는 잠들게 된다. 이 과정을 원자적으로 보장해주는게 guard일 뿐이다.
    - **setPark()**
        - Wakeup/Waiting Race를 해결한다.
        - setpark()는 현재 스레드가 운영체제에게 park 상태에 진입하기 직전임을 알리는 시스템 콜이다.
        - 이를 통해, "unpark가 park보다 먼저 호출되면 sleep하지 않는다." 라는 작업을 수행할 수 있다.

- **Condition Variable이란 무엇인가요?**
    - 특정 조건이 만족될 때까지 스레드가 기다리도록 하고, 조건이 만족되었을 때 기다리고 있는 스레드들을 깨워주는 대기열이다.

- **Condition Variable을 통해 유한 버퍼 문제를 어떻게 해결할 수 있을까요?**
    - 생산자는 버퍼가 차있는 동안 데이터를 생산할 수 없으므로, 소비자가 데이터를 소비할 때까지 wait을 통해 잠든다.
    - 소비자는 버퍼가 비어있는 동안 데이터를 소비할 수 없으므로, 생산자가 데이터를 생산할 때까지 wait을 통해 잠든다.
    - 생산자와 소비자 모두 조건이 만족되는 경우 signal을 통해 잠에서 깨어난다.
    - if문 대신 while문을 사용하여, 스레드가 잠에서 깨어나더라도 조건을 한 번 더 확인하게 한다.
        - Mesa semantics는 깨워진 스레드가 즉시 실행되지 않을 수도 있다는 약한 보장을 제공하고, Hoare semantics는 깨워진 스레드가 즉시 실행된다는 강한 보장을 제공한다. 대부분의 운영체제는 Mesa semantics 방식을 사용한다. (성능 비용)
    - 생산자와 소비자는 잠들고, 깨어나는 조건이 상이하므로 두 개의 CV를 이용한다.

- **세마포어가 무엇인지, 어떻게 동작하는지 설명해주세요.**
    
    세마포어는 운영체제에서 공유 자원에 대한 접근을 제어하기 위해 사용되는 정수값을 기반 동기화 도구이다.
    
    - **세마포어 값이 1 이상일 경우**
    `sem_wait()`가 호출되었을 때 세마포어의 값이 1 이상이면, 호출한 스레드는 즉시 반환된다. 이 경우, 세마포어 값을 1 감소시키고, 해당 스레드는 자원을 사용할 수 있게 된다.
    - **세마포어 값이 0일 때**
    호출한 스레드는 수행을 중단하고 대기 상태로 들어간다. 이후 다른 스레드가 `sem_post()`를 호출해 세마포어 값을 증가시키면, 대기 중인 스레드가 깨어나 실행을 재개한다.
    - **세마포어 값이 음수일 때**
    세마포어의 값이 음수라면, 이는 대기 중인 스레드의 수와 동일하다. 예를 들어, 세마포어 값이 -3이라면, 현재 3개의 스레드가 `sem_wait()`을 통해 대기 중임을 의미한다.
    - 조건 기반으로 스레드를 재우고 깨우는 경우 Mutex + CV, 단순히 자원 수 관리의 경우 세마포어가 직관적!

- **세마포어에서 실행 순서를 보장하는 법은 무엇인가요?**
    - 초기값을 0으로 설정하고, 늦게 실행될 스레드에서 `sem_wait`을 호출하면 된다.
        
        ```java
        #include <stdio.h>
        #include <pthread.h>
        #include <semaphore.h>
        
        sem_t sem;  // 세마포어 선언
        
        void* processA(void* arg) {
            printf("A: 작업 실행 중...\n");
            // 중요한 작업 수행
            sleep(1);
        
            printf("A: 작업 완료, B에게 signal 보냄\n");
            sem_post(&sem); // B를 깨움
            return NULL;
        }
        
        void* processB(void* arg) {
            sem_wait(&sem); // 세마포어가 0이면 여기서 블로킹됨
            printf("B: A 작업 완료 확인 후 실행 시작\n");
            return NULL;
        }
        
        int main() {
            pthread_t a, b;
            sem_init(&sem, 0, 0);  // 초기값 0 → B는 블로킹 상태로 시작
        
            pthread_create(&a, NULL, processA, NULL);
            pthread_create(&b, NULL, processB, NULL);
        
            pthread_join(a, NULL);
            pthread_join(b, NULL);
            sem_destroy(&sem);
            return 0;
        }
        ```
        

- **세마포어로 유한버퍼 문제를 해결하는 과정을 설명해주세요.**
    - `empty`와 `full` 두 개의 세마포어를 사용하여 여러 생산자와 소비자가 자원을 공유하도록 한다.
    - `sem_wait(&mutex)`와 `sem_post(&mutex)`을 통해 `put`, `get` 과정에서 Mutual Exclusion을 보장한다.
    - 첫째, `sem_wait(&mutex)` 도 추가하여 공통 자원에 대한 락을 구현해야 한다.
    - 둘째, `sem_wait(&mutex)` 을 먼저 확득하고 `sem_wait(&empty)`, `sem_wait(&full)` 을 획득하려고 하면 데드락 문제가 발생할 수 있다. 먼저  `sem_wait(&empty)`, `sem_wait(&full)` 을 획득한 후 공용 락 획득을 시도하는 방식으로 해결할 수 있다.

- **세마포어와 Mutex의 차이를 설명해주세요.**
    - 뮤텍스는 잠금(Locking) 메커니즘으로, 자원을 점유한 스레드만 잠금을 해제할 수 있기 때문에, 세마포어처럼 신호(sem_post)를 보낼 수 있는 기능은 없다.
    - 반면, 세마포어는 신호(Signaling) 메커니즘을 사용하여, 자원을 점유하지 않은 스레드도 신호(sem_post)를 보낼 수 있다.
    - 따라서, 이진 세마포어는 뮤텍스처럼 사용할 수 있지만, 뮤텍스는 세마포어처럼 사용할 수 없다.
    - 뮤텍스 사용 → 동기화의 목적이 자원 보호인 경우 더 안전하고 명확 (세마포어는 signal 추적 등 실수 유발)
    - 세마포어 → 실행 순서를 제어하고 싶은 경우

- **DeadLock(교착상태)에 대해 설명하고, 해결 방법에 대해 설명해주세요.**
    - DeadLock(교착상태)는, 두 개 이상의 프로세스나 쓰레드가 서로 자원을 기다리면서 무한히 대기하는 상태를 의미한다.
    - DeadLock이 발생하기 위한 조건은 4가지가 있다.
        - **상호 배제 (Mutual Exclusion)**
            - 한 자원에 여러 프로세스가 동시에 접근할 수 없다.
        - **점유 대기 (Hold and Wait)**
            - 하나의 자원을 소유한 상태에서 다른 자원을 기다린다.
        - **비선점 (Non-preemption)**
            - 프로세스가 어떤 자원의 사용을 끝낼 때까지 프로세스의 자원을 뺏을 수 없다.
        - **순환 대기 (Circular Wait)**
            - 각 프로세스가 순환적으로 다음 프로세스가 요구하는 자원을 갖고 있다.
    - **예방 (Prevention)**
        - 교착 상태 조건 중 하나를 제거함으로 데드락이 발생하지 않도록 예방하는 방식
        - 자원 낭비가 심하다.
    - **회피 (Avoidance)**
        - **데드락 발생 가능성을 인정하면서도 적절하게 회피하는 방식**
        - **Banker’s Algorithm**
            - 프로세스가 자원을 요구할 때 시스템은 자원을 할당한 후에도 안정 상태로 남아있게 되는지를 사전에 검사하는 알고리즘
            - 발생하지 않으면 자원을 할당하고, 발생하면 다른 프로세스가 자원을 해제할 때까지 대기한다.
            - 안전상태: 시스템이 교착상태를 일으키지 않으면서 각 프로세스가 요구한 최대 요구량만큼 필요한 자원을 할당해 줄 수 있는 상태
            - 항상 안전 상태를 유지할 수 있다는 장점이 있으나 **최대 자원 요구량을 미리 알아야 하고** **시뮬레이션을 매번 해야 하므로 비효율적이다.**
    - **회복 (Recovery)**
        - 은행원 알고리즘과 유사하게 시스템의 자원 할당 상태를 갖고 데드락이 발생했는지 여부를 탐색한다.
        - 탐지했다면 데드락을 회복한다.
            - 데드락 상태의 프로세스 모두 중단시키기
            - 프로세스를 하나씩 중단 시킬 때마다 탐지 알고리즘으로 데드락을 탐지하면서 회복시키기
            - 자원 섬점을 통해 해결하기(교착 상태에 있는 프로세스가 점유하고 있는 자원을 선점하여 다른 프로세스에 할당)
    - **스케줄링**
        - 애초에 같은 자원을 요구하는 스레드를 병렬 스케줄링 하지 않는 방법이 있다.

- **MySQL에서는 어떻게 DeadLock을 예방하나요? (회복)**
    - 많은 데이터베이스는 Detect and Recover 방식을 사용하고 있다. (트랜잭션이 자원을 어떻게 요청할지 예측하기 어렵고, 잘 설계된 트랜잭션과 쿼리 구조에서는 데드락이 거의 발생하지 않기 때문!
    - Deadlock 감지기가 주기적으로 실행되고, 자원의 순환 관계를 그래프를 통해 확인하며, Deadlock이 감지되는 경우 시스템을 재시작한다.
    - InnoDB는 트랜잭션 간 락 충돌을 줄이기 위해 같은 쿼리라도 항상 같은 순서로 레코드에 락을 걸도록 설계되어 있다.
        
        ```sql
        -- 트랜잭션 A
        SELECT * FROM users WHERE id IN (1, 2) FOR UPDATE;
        
        -- 트랜잭션 B
        SELECT * FROM users WHERE id IN (2, 1) FOR UPDATE;
        ```
        
    - 위를 통해 순환대기를 방지한다.

- **Windows에서는 어떻게 DeadLock을 처리하나요? (무시)**
    - Windows는 커널 레벨에서 락 충돌로 데드락이 발생해도 직접 해결하지 않는다!
    - 메인 스레드가 지속적으로 응답하지 않는다는 현상을 대기해서 알려줄 뿐이다.
        - GUI 애플리케이션이 mutex A → mutex B를 락
        - 다른 스레드가 mutex B → mutex A 락을 시도하면서 데드락
        - 사용자는 "프로그램이 응답하지 않음" 메시지를 보게 됨

- **DeadLock 회복의 예시를 알려주세요.**
    - **다중 계좌 이체 시스템**
        - 여러 사용자가 계좌 간 송금을 동시에 요청
        - 각각의 이체는 A → B, B → C 등 복수의 자원(계좌 락)을 점유해야 완료됨
        - 중간에 서로의 계좌를 기다리게 되면 데드락 발생
    - 데드락이 발생하면, 운영체제 또는 트랜잭션 매니저가 충돌 중인 트랜잭션 중 하나를 “희생”해서 강제로 롤백 시킨다.

- **DeadLock은 왜 발생하나요?**
    - **복잡한 의존성**
        
        코드가 커지고 복잡해질수록, 서로 다른 컴포넌트 간에 복잡한 의존 관계가 생기게 된다. 이로 인해 의존성 순환 문제가 생기기 쉬워진다.
        
    - **캡슐화(encapsulation)의 특성**
        
        캡슐화는 구현 세부 사항을 숨기고, 소프트웨어를 모듈 단위로 쉽게 구축할 수 있도록 하는 중요한 개념이다. 그러나 캡슐화는 Locking과 잘 어울리는 개념이 아닌데, 이해가 부족한 상태로 여러 모듈을 채택할수록 동기화 문제가 생기기 쉬워지기 때문이다.
        

- **식사하는 철학자 문제의 해결 방법을 설명해주세요.**
    
    모든 철학자가 방에 입장한 후, 각자의 왼쪽포크를 5명이 모두 드는 경우에 DeadLock이 발생합니다.
    
    1. 5명 모두 자신의 왼쪽 포크를 들고 있으므로 '점유대기'
    2. 남이 포크를 뺏어주지 않음 '비선점'
    3. 서로 오른쪽 포크를 놓기만을 기다림 '순환형 대기'
    4. 각 포크에 대해 한 사람만 들 수 있음 '상호 배제'
    
    이 문제를 해결하기 위해서, 카운팅 세마포어를 사용합니다.
    
    방에 대한 입장 정원을 카운팅 세마포어로 설계해, 최대 4명만 들어온다면 방 안의 모든 사람들이 왼쪽 포크를 든다 하더라도 DeadLock이 일어나지 않습니다.
