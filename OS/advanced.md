- **32비트와 64비트 운영체제가 다른 점을 전부 설명해주세요.**
    - 32비트 운영체제에서는 하나의 포인터가 4바이트(32비트) 크기이므로, 표현할 수 있는 주소 공간은 2³² = 약 4GB입니다. 이 중 커널이 일정 부분을 사용하므로 실제 사용자 프로세스가 사용할 수 있는 공간은 보통 2~3GB 수준입니다. 반면, 64비트 운영체제는 포인터가 8바이트(64비트)이기 때문에 이론적으로는 2⁶⁴ = 16엑사바이트(EB)까지 주소를 지정할 수 있습니다. 현실적으로는 하드웨어와 OS의 제한으로 보통 수 테라바이트(TB)까지 지원됩니다.
    - CPU의 레지스터(Register) 크기도 32비트와 64비트에서 다릅니다. 레지스터는 연산에 필요한 데이터를 저장하는 초고속 저장소로, 64비트 CPU에서는 더 큰 정수나 주소를 한 번에 처리할 수 있어, 수치 계산, 메모리 접근, 시스템 콜 등에서 성능이 향상됩니다.
    - 64비트 프로그램은 포인터가 8바이트이므로, 동일한 로직이라도 더 많은 메모리를 사용합니다. 예를 들어, 포인터를 많이 사용하는 자료구조에서는 32비트보다 메모리 낭비가 더 클 수 있습니다. 반면, 주소 공간이 넉넉하기 때문에 대용량 메모리를 사용할 수 있다는 장점이 있습니다.
    - 32비트는 포인터 크기가 작기 때문에 캐시에 더 많은 주소를 저장할 수 있어, **캐시 히트율이 높은 작업**(예: 메모리 지역성 높은 반복 처리 등)에서는 오히려 유리한 경우도 있습니다. 하지만 이는 특정 상황에 한정되며, 대체로는 64비트가 더 성능이 좋습니다.
    
     
    
- **스택 오버플로우를 커널이 어떻게 인지할까요?**
    - 리눅스나 유닉스 계열 운영체제에서는, 프로세스의 가상 주소 공간 중 상위 주소 영역을 스택으로 사용하겠다는 것을 프로세스 생성 시점에 미리 정해서 예약해 둔다.
    - 또한, 스택과 다른 영역이 하나의 페이지 안에 섞이지 않도록 운영체제가 설계한다. 즉, 메모리 보호 단위인 페이지 경계를 기준으로 스택, 힙, 코드 등 주요 영역을 정확히 "페이지 단위"로 구분하여 매핑한다.
    - 따라서 스택 페이지 아래에 Guard Page라는 접근 불가능한 페이지(Guard Page)를 설정하여 스택 오버플로우를 인지할수 있다. (Segmentation Fault)
    
- **자바 프로그램 실행 시 전체 과정을 설명해주세요.**
    
    JVM은 운영체제에 의해 하나의 프로세스로 실행되며, 자신만의 가상 주소 공간(Virtual Address Space)을 부여받습니다. JVM 입장에서 보면 이 메모리 공간은 하나의 연속된 큰 메모리처럼 보이지만, 실제 물리 메모리는 그렇지 않습니다.
    
    운영체제는 페이징 기법(Paging)을 통해 이 가상 주소 공간을 고정된 크기(보통 4KB)의 페이지 단위로 분할하고, 이를 물리 메모리 프레임(frame)에 매핑합니다. 이 매핑 정보는 페이지 테이블(Page Table)에 저장되며, CPU는 이 정보를 참조하여 가상 주소를 실제 물리 주소로 변환합니다.
    
    CPU는 이 매핑 속도를 높이기 위해 최근에 사용한 주소 변환 정보를 TLB(Translation Lookaside Buffer)라는 고속 캐시에 저장합니다. JVM이 특정 가상 주소를 접근할 때, 먼저 TLB에서 해당 가상 주소의 물리 주소 매핑을 찾고, 없으면 페이지 테이블을 조회하게 됩니다.
    
    결과적으로, JVM은 자신이 사용하는 힙, 스택, 메서드 영역 등을 연속된 메모리 공간처럼 인식하지만, 실제로는 페이지 단위로 분산된 물리 메모리 위에 존재하며, 이들 사이의 주소 변환은 전부 OS와 하드웨어에 의해 자동으로 처리됩니다.

- **우리가 사용하는 시스템 콜의 예시를 들어주세요.**
    - `read()`, `write()` → 파일 또는 터미널로부터 데이터 입출력
    - `open()`, `close()` → 파일 디스크립터 열기/닫기
    - `fork()` → 새로운 프로세스 생성
    - `exec()` → 새로운 프로그램 실행
    - `wait()` → 자식 프로세스 종료 대기
    - `exit()` → 프로세스 종료
- **시스템 콜이, 운영체제에서 어떤 과정으로 실행되는지 설명해 주세요.**
    - 사용자 프로그램이 read() 같은 시스템 콜 함수를 호출한다.
        - `read()`는 사실 C 라이브러리 함수지만, 내부에서 운영체제에게 요청을 전달한다.
    - 시스템 콜 번호와 파라미터가 준비된다.
        - 운영체제는 모든 시스템 콜에 고유한 번호(ID)를 부여한다.
        - 전달할 값(파일 디스크립터, 버퍼 주소, 크기)을 레지스터 등에 담는다.
            - **파일 디스크립터:** 파일 번호
            - **주소:** 읽은 결과를 저장할 공간(`char[100]`배열 등)
            - **크기:** 몇 바이트까지 읽을지?
    - Trap 명령어로 커널에게 신호를 준다.
    - 커널이 시스템 콜 번호를 확인한다.
        - 내부에 있는 `sys_read()` 같은 커널 함수를 찾아 실행
    - 유저 스택과 유사하게, 커널 스택으로 커널 함수 작업을 수행한다.
    - 커널이 요청을 처리한다.
    - 작업이 끝나면 다시 유저 모드로 돌아간다.
- **시스템 콜의 유형에 대해 설명해 주세요.**
    1. **프로세스 제어(Process Control)**: `fork()`, `exec()`, `exit()`
    2. **파일 조작(File Management)**: `open()`, `read()`, `write()`, `close()`
    3. **장치 조작(Device Management)**: `ioctl()`, `read()`, `write()`
    4. **정보 유지(Information Maintenance)**: `getpid()`, `alarm()`, `sleep()`
    5. **통신(Communication)**: `pipe()`, `shmget()`, `msgsnd()` (프로세스 간 통신)
    6. **보안(Security)**: `setuid()`, `getuid()`
- **운영체제의 Dual Mode 에 대해 설명해 주세요.**
    
    Dual Mode는 CPU가 **User Mode**와 **Kernel Mode** 두 가지 모드로 동작할 수 있음을 의미합니다.
    
    - **User Mode**는 사용자 프로그램이 실행되는 상태이며, 제한된 명령어와 자원만 사용 가능합니다.
    - **Kernel Mode**는 운영체제가 실행되는 상태로, 하드웨어 자원에 직접 접근하거나 특권 명령어를 실행할 수 있습니다.
        
        이러한 모드 구분을 통해 사용자 프로그램의 오류나 악성 행동이 시스템 전체에 영향을 주는 것을 방지합니다.
        
- **왜 유저모드와 커널모드를 구분해야 하나요?**
    
    유저모드와 커널모드를 구분하는 가장 큰 이유는 **보안성과 안정성 보장**입니다.
    
    - 사용자 프로그램이 하드웨어나 시스템 자원에 직접 접근한다면, 버그나 악의적인 코드로 인해 시스템이 손상될 수 있습니다.
    - 이를 방지하기 위해, 민감한 작업은 오직 커널 모드에서만 수행하도록 제한하고, 유저 모드에서는 시스템 콜을 통해 간접적으로 요청하도록 설계합니다.
        
        이러한 구조 덕분에 운영체제는 하나의 프로그램의 문제로 전체 시스템이 영향을 받지 않도록 보호할 수 있습니다.
        
- **서로 다른 시스템 콜을 어떻게 구분할 수 있을까요?**
    
    운영체제는 시스템 콜 번호(System Call Number)를 통해 각 시스템 콜을 구분합니다.
    
    - 시스템 콜 라이브러리는 호출하려는 시스템 콜에 고유한 번호를 할당하여, 커널에 trap 명령어로 전달할 때 이 번호를 함께 보냅니다.
    - 커널은 이 번호를 확인해 해당하는 시스템 콜 핸들러를 찾아 실행합니다.
        
        예를 들어, Linux에서는 `open()`이 2번, `write()`가 1번처럼 고유한 번호가 있습니다. 이 덕분에 여러 시스템 콜을 정확히 구분하여 처리할 수 있습니다.

- **인터럽트 Polling 방식에 대해 설명해 주세요.**
    
    Polling 방식은 CPU가 I/O 장치의 상태를 주기적으로 직접 확인(polling)하여, 작업 처리가 가능한지를 검사하는 방식입니다. 이 방식은 구조가 단순하고 구현이 쉬운 장점이 있지만, 장치가 응답할 때까지 CPU가 반복적으로 확인을 수행하기 때문에 CPU 자원이 낭비되고 비효율적일 수 있습니다. 반면 인터럽트 방식은 장치가 작업을 완료했을 때 CPU에 알리는 구조라, CPU가 다른 작업을 하다가 필요한 시점에만 응답할 수 있어 효율적입니다. 따라서 실시간성이 크지 않은 간단한 시스템에서 polling이 사용되기도 하지만, 대부분의 운영체제는 인터럽트 기반으로 동작합니다.
    
- **동시에 두 개 이상의 인터럽트가 발생하면, 어떻게 처리해야 하나요?**
    
    동시에 두 개 이상의 인터럽트가 발생하는 경우, 운영체제는 인터럽트 우선순위(Priority)를 기준으로 처리 순서를 결정합니다. CPU는 현재 수행 중인 인터럽트보다 우선순위가 높은 인터럽트가 들어오면 그 처리 중에도 중첩(interrupt nesting)해서 상위 인터럽트를 먼저 처리합니다. 반대로, 우선순위가 낮거나 동등한 인터럽트는 대기 큐에 저장되었다가, 현재 인터럽트 처리가 끝난 후 순차적으로 처리됩니다. 이러한 방식으로 운영체제는 다중 인터럽트를 논리적이고 안정적으로 처리합니다.
    
- **프로그램이 컴파일 되어, 실행되는 과정을 간략하게 설명해 주세요.**
    1. 소스 코드 작성,
    2. 컴파일러가 소스 코드를 목적 코드(.o)로 변환
    3. 링커(Linker)가 여러 목적 파일과 라이브러리를 연결하여 실행 파일(.exe)을 생성
    4. 로더(Loader)가 실행 파일을 메모리에 적재하고, 초기화한 뒤 프로세스를 실행
- **우리는 흔히 `fork()`, `exec()` 시스템 콜을 사용하여 프로세스를 적재할 수 있다고 배웠습니다. 로더의 역할은 이 시스템 콜과 상관있는 걸까요? 아니면 다른 방식으로 프로세스를 적재할 수 있는 건가요?**
    
    `exec()` 내부에서 로더(Loader)가 실제로 동작합니다. 즉, 로더는 `exec()` 시스템 콜과 밀접하게 연결되어 있으며, 실행 파일을 메모리에 적재하고 실행 환경을 초기화하는 실질적인 작업을 수행하는 주체입니다. 결과적으로 로더는 `exec()`를 통해 간접적으로 호출되어 프로세스를 적재하는 방식으로 작동합니다.

- **리눅스에서, 프로세스와 스레드는 각각 어떻게 생성될까요?**
    
    리눅스에서 프로세스는 주로 `fork()` 시스템 콜을 통해 생성됩니다. `fork()`는 부모 프로세스를 그대로 복제해 새로운 자식 프로세스를 만들고, 이후 `exec()` 시스템 콜을 통해 다른 실행 파일로 메모리를 교체해 실행할 수 있습니다.
    
    스레드 생성은 `clone()` 또는 `pthread_create()` 함수를 사용합니다. 이때 `clone()`은 여러 플래그를 통해 메모리 공간, 파일 디스크립터, 스택 등을 다른 스레드와 공유할지 여부를 세밀하게 제어할 수 있는 시스템 콜입니다.
    
    - 자바에서 `new Thread` 로 스레드를 생성하면 자동으로 기본적으로 부모 스레드와 동일한 프로세스 내에서 메모리를 공유하는 "스레드"를 생성합니다.
- **자식 프로세스가 상태를 알리지 않고 죽거나, 부모 프로세스가 먼저 죽게 되면 어떻게 처리하나요?**
    
    자식 프로세스가 종료될 때, 종료 상태는 부모 프로세스가 `wait()` 또는 `waitpid()`로 수거해야만 완전히 제거됩니다. 만약 부모가 수거하지 않으면, 자식은 좀비 프로세스(Zombie) 상태로 남게 되어 커널의 프로세스 테이블을 계속 차지하게 됩니다.
    
    부모 프로세스가 먼저 종료되면 자식 프로세스는 고아 프로세스(Orphan)가 됩니다. 이때 리눅스 커널은 해당 고아 프로세스들을 자동으로 `init(1)` 프로세스(또는 systemd)가 상속받아 관리하게 합니다.
    
- **리눅스는 프로세스가 일종의 트리를 형성하고 있습니다. 이 트리의 루트 노드에 위치하는 프로세스에 대해 설명해 주세요.**
    
    리눅스에서 모든 프로세스는 부모-자식 관계를 갖는 트리 구조로 존재합니다. 이 트리의 루트 노드에 해당하는 프로세스는 PID 1번 프로세스인 `init`(또는 `systemd`)입니다.
    
    이 프로세스는 부팅 시 커널이 처음으로 실행하는 사용자 공간 프로세스로, 시스템의 기본적인 서비스와 데몬(하드웨어 감지, 네트워크 dhcp 등 자동 시작)을 초기화하고, 고아가 된 자식 프로세스를 대신 수거하는 역할도 수행합니다. `init` 또는 `systemd`는 항상 살아있어야 하며, 만약 이 프로세스가 종료되면 시스템 전체가 정상 동작할 수 없기 때문에 커널 패닉으로 이어질 수 있습니다.
    
- **프로세스와 스레드는 컨텍스트 스위칭이 발생했을 때 어떤 차이가 있을까요?**
    
    프로세스 간 전환은 주소 공간이 완전히 달라지기 때문에, 페이지 테이블, 가상 메모리 매핑, 파일 디스크립터 등 많은 자원을 함께 교체해야 하며, TLB도 flush되어야 하기 때문에 상대적으로 비용이 매우 큽니다.
    
    스레드는 동일한 프로세스 내에서 실행되므로 주소 공간과 자원들을 공유합니다. 따라서 스레드 간 컨텍스트 스위칭은 레지스터, 스택 포인터, 프로그램 카운터 등 실행 흐름만 저장·복원하면 되므로 훨씬 가볍고 빠르게 이루어집니다.
    
- **컨텍스트 스위칭이 발생할 때, 기존의 프로세스 정보는 커널 스택에 어떠한 형식으로 저장되나요?**
    - **커널 저장 형태**
        - 스레드는 자신의 상태 정보(task_struct)를 커널 메모리 어딘가에 저장해놓는다. (이게 PCB/TCB)
        - 그리고 자신만의 전용 커널 스택도 하나씩 갖고 있다. (함수 호출, 레지스터 저장 등에 사용)
        - 이 커널 스택의 맨 아래 부분에 `thread_info`라는 작은 구조가 들어 있다.
        - 이 `thread_info`에는 자신의 `task_struct`를 가리키는 포인터가 들어 있다.
        - 이 `task_struct` 에 바로 PCB+TCB에 대한 정보가 들어있는 것이다.
        - 이 때, TCB는 스레드마다 독립적이기에 직접 저장되어 있고, PCB는 공유되기 때문에 포인터가 저장되어 있다.
        - 그 포인터가 가리키는 PCB 정보는 커널 힙 메모리 영역에 동적으로 할당돼 있다.
    - **컨텍스트 스위칭 과정**
        - A의 `task_struct` 에 스택 포인터, 레지스터 값 등을 전부 저장
        - B의 `task_struct` 구조체에서 스택 포인터, 레지스터 값 등을 전부 복구
- **Thread 스택과 Thread Local의 크기는 각각 어느 정도인가요?**
    - 스레드마다 자신만의 스택 메모리인 스택은 1MB
    - Thread Local의 경우 동적으로 늘어나고, 힙에 저장된다. 스레드 안의 ThreadLocalMap이 그 힙 객체를 가리키고 있을 뿐!

- **프로세스 주소 공간에서, 초기화 하지 않은 변수들은 어디에 저장될까요?**
    
    초기화하지 않은 전역 변수나 static 변수는 BSS(Block Started by Symbol) 영역에 저장됩니다. BSS는 데이터 세그먼트 중 초기값이 없는 변수들을 위한 공간이며,
    운영체제가 실행 시 0으로 초기화해줍니다. 이와 달리 초기값이 있는 전역 변수는 data 영역에 저장됩니다.
    
- **일반적인 주소공간 그림처럼, Stack과 Heap의 크기는 매우 크다고 할 수 있을까요? 그렇지 않다면, 그 크기는 언제 결정될까요?**
    
    일반적으로 Stack과 Heap의 실제 크기는 물리적으로 매우 크지는 않습니다. Stack 크기는 보통 OS 또는 실행 환경에 따라 고정 크기로 제한되며, Heap 크기는 프로그램 실행 중 동적 할당 요청에 따라 점진적으로 확장됩니다.
    
    - `brk` 는 프로세스의 힙 끝(=brk 포인터)을 앞으로 조금씩 늘리는 방식
    - `mmap()`은 가상 주소 공간의 아무 데나 빈 공간에 메모리를 매핑하는 방식
- **Stack과 Heap 공간에 대해, 접근 속도가 더 빠른 공간은 어디일까요?**
    
    일반적으로 Stack의 접근 속도가 Heap보다 빠릅니다. Stack은 함수 호출 시 컴파일 타임에 크기가 결정되고, LIFO 방식으로 연속적인 메모리 구조를 갖기 때문에 캐시 친화적(함수 호출될 때마다 메모리를 인접하게 쓰는 구조)입니다. 반면 Heap은 동적 메모리로 포인터 기반의 비연속적 구조이며, 할당과 해제가 복잡하여 상대적으로 느립니다.
    
- **스택이 매우 커진다면 힙은 불필요할까요?**
    
    그렇지 않습니다. Stack과 Heap은 용도가 전혀 다르기 때문에 서로를 대체할 수 없습니다. Stack은 짧은 생명주기를 갖는 지역 변수나 함수 호출 정보를 저장하기에 적합하고, Heap은 동적으로 크기를 지정하거나 장기간 유지되는 데이터를 저장할 때 필요합니다.
    
    멀티스레딩 환경에서 여러 스레드가 동시에 접근할 필요성이 있는 대상 메모리가 필요할 경우, 스택에서는 함수 리턴시 그 공간들이 모두 사라지기 때문에 이를 구현하기 어렵습니다.
    
- **스택 영역과 힙 영역은 정말 자료구조의 스택/힙과 연관이 있는 걸까요? 만약 그렇다면, 각 주소공간의 동작과정과 연계해서 설명해 주세요.**
    
    스택(Stack) 영역은 함수 호출 시마다 프레임을 쌓고, 반환 시에 제거하는 구조로
    자료구조의 LIFO(Last-In-First-Out) 방식과 동일하게 동작합니다.
    
    반면 힙(Heap) 영역은 자료구조의 힙과 직접적인 구조적 연관은 없지만, 비정형적으로 동적 할당되는 메모리 공간이라는 점에서 “뒤죽박죽인 구조”라는 의미의 힙에서 이름이 유래되었습니다. 즉, 메모리에서의 힙은 할당과 해제가 순차적이지 않고 자유롭다는 의미에서 그렇게 불립니다.
    
- **IPC의 Shared Memory 기법은 프로세스 주소공간의 어디에 들어가나요? 그런 이유가 있을까요?**
    
    Shared Memory는 각 프로세스의 가상 주소 공간 내 Heap 근처의 사용자 영역에 매핑됩니다. 이는 공유 메모리를 일반 변수처럼 접근할 수 있도록 하기 위함이며, OS는 각 프로세스의 가상 주소 공간에 동일한 물리 메모리 영역을 매핑하여 공유를 실현합니다. 커널 공간이 아닌 사용자 영역에 위치하는 이유는 빠른 접근성과 사용자 프로세스 간 직접 데이터 교환을 가능하게 하기 위해서입니다.
    
    - 하나의 물리 메모리 블록이, 여러 프로세스의 가상 주소 공간에 공유 매핑!!
- **스택과 힙 영역의 크기는 언제 결정되나요? 프로그램 개발자가 아닌, 사용자가 이 공간의 크기를 수정할 수 있나요?**
    
    Stack의 기본 크기는 컴파일러나 운영체제가 정한 기본값으로 정해지며, Heap의 크기는 프로세스가 실행 중 요청하는 만큼 동적으로 결정됩니다. 사용자는 운영체제 설정이나 실행 시 인자 등을 통해 Stack 및 Heap의 최대 크기를 제한하거나 변경할 수 있습니다.
    
    - 프로세스에는 메인 스레드의 스택이 존재하고, 그 외에 생성된 스레드들도 각자 고유한 스택을 갖는다. 즉, 스택은 스레드 단위로 존재한다!
    - 이러한 스택은 OS, 스레드 라이브러리 별로 기본 값이 정해져있는데,  OS 설정 또는 스레드 생성 시 변경 가능하다.
    - 리눅스 기준 메인 스래드 스택은 8MB, 서브 스레드 스택은 2MB가 디폴트!

- **DMA(Direct Memory Access)에 대해 설명해주세요.**
    
    데이터의 이동에는 CPU의 개입이 필요합니다. 그러므로 다량의 데이터가 이동하는 과정에서는 CPU에 많은 부하가 걸리게 됩니다. 따라서 CPU를 거치지 않고 직접 데이터를 전송하는 방법인 DMA를 사용합니다.
    
- **메모리 할당 중, 연속(Contiguous) 방식과 불연속(Non-Contiguous) 방식에 대해 설명해주세요.**
    
    연속 할당 방식은, 프로세스 이미지가 분리되지 않은 온전한 프로세스를 메인 메모리에 적재하는 방식입니다. 연속 할당 방식에는 크게 2가지가 있으며 '고정 길이 할당'과 '가변 길이 할당'이 있습니다.
    
    - 고정 길이 할당 : 메모리를 고정된 길이로 파트를 분리하고, 프로세스를 해당 파트에 삽입합니다. 고정된 길이의 파트 내에 프로세스가 들어가므로, 여백이 생길 수 있는데 이것을 '내부 단편화'라고 합니다.
    - 가변 길이 할당 : 메모리를 프로세스의 길이에 알맞게 파트를 분리하고, 해당 프로세스를 적재합니다. 가변된 길이이므로 내부 단편화는 발생하지 않지만, 가변적인 길이 할당에 의해 일부분이 남으므로 '외부 단편화'가 발생합니다.
    
    불연속 할당 방식은, 프로세스가 연속된 이미지가 아닌 분리된 이미지로 구성되어 메인 메모리에 적재하는 방식입니다. '페이징'과 '세그멘테이션' 방식이 있습니다.
    
    - 페이징 : 프로세스를 동일한 크기의 페이지로 분리, 메모리는 해당 페이지와 동일한 크기의 프레임으로 분리해서 메인 메모리에 불연속적으로 저장하는 방식입니다. 만약 프로세스가 13MB이고 페이지가 4MB라면, 한 페이지는 1MB가 됩니다. 프레임은 무조건 4MB로 분리했으므로 3MB의 '내부단편화'가 발생할 수 있습니다. (연속 할당 방식보다는 적게 발생합니다.)
    - 세그멘테이션 : 프로세스를 가변적인 크기의 세그먼트로 분리하고 메모리에 적재합니다. 주로 논리적인 블록단위 세그먼트로 Code, Data, Stack & Heap으로 분리할 수 있습니다. 세그멘테이션 역시 '외부 단편화'가 발생합니다.
- **실제 리눅스와 윈도우에서의 메모리 가상화를 설명해주세요.**
    - 현대 Windows와 Linux는 모두 세그먼트를 무시하고 페이징 기반으로 메모리를 관리한다.
    - 페이지 교체는 각각 윈도우의 경우 Working Set 기반으로, 리눅스의 경우 LRU 변형(Clock Algorithm) 알고리즘을 사용한다.
    - Thrashing 발생 시 프로세스 중단 또는 프레임 조절 방식으로 대응한다.
- **메모리의 연속할당 방식 네 가지를 설명해주세요.**
    - **First Fit**
        - 처음으로 발견된 충분히 큰 빈 공간에 메모리를 할당합니다.
        - 검색 속도가 빠르고 구현이 단순하지만, 앞쪽에 작은 조각들이 많이 남아
        외부 단편화가 쉽게 발생할 수 있습니다.
    - **Next-Fit**
        - First Fit과 유사하지만, 할당 요청 시 리스트의 시작부터 검색하지 않고, 마지막으로 검색이 끝난 위치부터 검색을 시작합니다.
        - 이렇게 하면 Free List의 특정 구간이 반복적으로 검색되는 것을 피할 수 있지만, 검색 효율이 떨어질 수 있습니다.
    - **Best-Fit**
        - 요청 크기보다 크거나 같은 공간 중 가장 작은 블록을 찾아 할당합니다.
        - 메모리 낭비를 줄일 수 있지만, 가장 작은 블록을 찾기 위해 전체 탐색이 필요하므로 검색 오버헤드가 크고, 작은 조각들이 더 많이 발생하는 경우가 있습니다. (남은 공간이 의미 없을 만큼 작을지도!)
    - **Worst-Fit**
        - Best Fit과는 반대로, 가장 큰 (여유 있는) Free Chunk를 찾아 요청된 메모리 크기만큼 할당한 후, 남은 메모리는 Free List에 유지합니다.
        - 큰 Chunk를 할당하므로 남은 메모리 조각이 여전히 크고 유용할 가능성이 높지만, 공간이 비효율적으로 사용돨 수 있습니다. (남은 공간이 의미 있을 가능성이 크다!)
- **Worst-Fit 은 언제 사용할 수 있을까요?**
    - Worst-Fit은 큰 블록을 덜 쪼개기 때문에 작은 요청 처리 후에도 재사용 가능한 큰 공간을 남길 수 있다는 장점이 있다.
    - 따라서 대부분의 요청은 작지만, 이후 큰 요청이 자주 발생하는 패턴에서 사용할 경우 유용할 수 있다.
- **리눅스에서는 실제로 어떤 연속 할당 방식을 사용하나요?**
    - 사용자 공간 (우리가 malloc, new 등으로 사용하는 영역)
        - 리눅스는 `malloc()`을 하면 내부적으로 `brk()` 또는 `mmap()`을 통해 힙을 요청한다.
        - 이 때 이 메모리를 관리하는 건 OS가 아니다! C의 경우 라이브러리의 구현체, 자바의 경우 JVM이 `mmap()` 을 호출한다.
    - 커널 공간 (실제 물리 메모리를 할당)
        - **리눅스는 Buddy System을 쓴다!**
            - 메모리를 2의 거듭제곱 단위(4KB, 8KB, 16KB, ..., 1MB, ...)로 관리
            - 요청이 들어오면 딱 맞거나 가장 가까운 큰 블록을 나눠서 할당
            - 인접 블록이 둘 다 free면 합쳐서(buddy) 더 큰 블록으로 만듦
            - 고정적으로 할당하기에, 가변 할당 방식인 Fit에 비해 단편화를 줄이고 빠르게 할당하고 병합할 수 있다!
        - **Slab Allocator**
            - Slab Allocator는 같은 종류의 커널 객체들을 위한 미리 할당된 메모리 캐시(pool)를 관리하는 메커니즘이다.
            - 같은 크기의 객체들을 위한 슬랩 캐시(slab cache)를 만들고,
            - 그 캐시에 미리 메모리를 여러 개 확보한 다음, 할당/해제 요청이 들어오면 그냥 꺼내주고, 돌려받는 구조

- **어떤 주소공간이 있을 때, 이 공간이 수정 가능한지 확인할 수 있는 방법이 있나요?**
    
    페이지 테이블을 생성할 때 메모리 보호를 위해 추가적인 비트를 부여할 수 있습니다. Read-Write/Read-only 비트, Valid-invalid 비트 등을 설정 가능합니다.
    
- **32비트에서, 페이지의 크기가 1KB 이라면 페이지 테이블의 최대 크기는 몇 개일까요?**
    - 메모리 최대 크기 2^32 / 페이지 크기 2^10 = 2^22 개
    - 2^32는 4GB이다!
- **32비트 운영체제는 램을 최대 4GB 까지 사용할 수 있습니다. 이 이유를 페이징과 연관 지어서 설명해 주세요.**
    
    32비트 CPU는 하나의 주소가 최대 2³² = 4GB의 주소 공간만 표현할 수 있습니다.
    페이징 시스템에서 가상 주소는 [페이지 번호 + 페이지 오프셋] 형태로 구성되며,
    페이지 번호 역시 32비트 주소 공간 안에서 표현되므로, 최대 4GB의 가상 메모리까지만 관리할 수 있습니다.
    
    이는 물리적 메모리와 직접 연결되지 않더라도, 가상 주소 공간의 한계로 인해 운영체제는 단일 프로세스에 대해 최대 4GB까지만 매핑할 수 있다는 뜻입니다.
    
- **C/C++ 개발을 하게 되면 Segmentation Fault 라는 에러를 접할 수 있을텐데, 이 에러는 세그멘테이션/페이징과 어떤 관계가 있을까요?**
    
    Segmentation Fault는 프로세스가 허용되지 않은 메모리 영역에 접근했을 때 발생하는 오류입니다. 현대 운영체제는 페이징 기반 메모리 보호 기법을 사용하며, 각 페이지마다 접근 권한이 존재합니다.
    
    만약 유저 프로세스가 접근 권한이 없는 페이지를 읽거나 쓰거나 실행하려 할 경우,
    하드웨어가 페이지 테이블을 조회하여 이를 감지하고, 페이지 보호 위반 예외(Page Fault)를 발생시킵니다. 이 예외를 처리하는 과정에서 커널은 해당 접근이 불법이라고 판단하면 Segmentation Fault 신호(SIGSEGV)를 프로세스에 전달합니다.
    
- **코어가 여러개라면, TLB는 어떻게 동기화 할 수 있을까요?**
    
    TLB 캐시의 불일치 문제를 해결하기 위한 동기화 메커니즘이 바로 TLB Shootdown입니다.
    
    - 운영체제는 어떤 페이지 엔트리를 수정하거나 삭제할 때, 그 페이지가 다른 코어의 TLB에 존재할 수 있음을 인식합니다.
    - 따라서 커널은 해당 페이지의 TLB 엔트리를 모든 코어에서 무효화해야 합니다.
    - OS는 다른 프로세스에게 다른 CPU 코어들에게 인터럽트를 보냅니다.
    - 해당 코어는 인터럽트를 받고, 해당 페이지에 대한 TLB 엔트리를 명시적으로 flush(무효화)합니다.
- **TLB 관점에서, Context Switching 발생 시 어떤 변화가 발생하는지 설명해 주세요.**
    
    단순히 생각하면, 프로세스가 바뀌기 직전에 현재 프로세스의 엔트리의 Valid Bit을 0으로 전부 바꿔주는 방법을 생각할 수 있다. (TLB에서 말하는 Valid Bit은 매핑 정보의 유효성으로, 해당 주소 공간의 사용 여부를 나타내는 Page Table의 Valid Bit과는 아예 다른 개념이다.)
    
    하지만 Context Switching이 일어날 때마다 특정 프로세스의 Valid Bit을 전부 바꾸는 것은 비효율적이고 성능 저하를 초래할 수 있다. (이 또한 연산이므로) 따라서, 간단히 ASID(Address Space Identifier)를 기록하여 프로세스를 구분할 수 있다.

- **단기, 중기, 장기 스케쥴러에 대해 설명해 주세요.**
    
    운영체제에서 단기, 중기, 장기 스케줄러는 각각 다른 시점과 목적에서 프로세스의 실행 흐름을 제어합니다.
    
    - 장기 스케줄러(Long-term scheduler)는 디스크에 존재하는 작업 중 일부를 메모리에 올려 실행 준비 상태로 만드는 역할을 하며, 시스템 부하를 조절하는 데 사용됩니다.
    - 중기 스케줄러(Mid-term scheduler)**는 실행 중이던 프로세스를 일시적으로 메모리에서 디스크로 내보내는 스와핑(Swapping) 작업을 수행하며, 메모리 부족 시 유휴 프로세스를 제거해 전체 시스템의 응답성을 향상시킵니다.
    - 마지막으로 단기 스케줄러(Short-term scheduler)는 Ready Queue에 있는 프로세스 중에서 하나를 선택하여 CPU를 할당하는 역할로, 실제 CPU 스케줄링의 중심이 되는 컴포넌트입니다.
- **현대 OS에는 단기, 중기, 장기 스케쥴러를 모두 사용하고 있나요?**
    
    현대 OS는 단기 스케줄러만을 명시적으로 사용하며, 장기·중기 스케줄러는 명확히 분리되어 있지 않거나 자동화된 메커니즘에 통합되어 있습니다. 
    
    현대 OS는 자원 여유와 자동화된 리소스 관리 덕분에, 과거처럼 장기/중기 스케줄러를 명시적으로 두지 않아도 운영이 가능합니다. 대신 그 역할은 자동화된 커널 메커니즘에 흡수되거나, 단기 스케줄러 중심으로 단순화되어 효율성과 응답성을 높이도록 진화한 것이죠.
    
- **프로세스의 스케줄링 상태에 대해 설명해 주세요.**
    - **New**: 생성된 직후, 아직 OS에 등록되지 않은 상태
    - **Ready**: 메모리에 적재되어 CPU 할당을 기다리는 상태
    - **Running**: CPU를 점유하고 실행 중인 상태
    - **Waiting(Blocked)**: 입출력 등 외부 이벤트를 기다리는 상태
    - **Terminated**: 실행이 끝나거나 강제 종료된 상태입니다.
- **어떻게 새로운 프로세스가 도착했음을 알고, 그것이 더 짧은 프로세스임을 알고, CPU 제어권을 넘기는건가요?**
    - 실제로 운영체제가 프로세스의 정확한 실행 시간을 미리 아는 것은 불가능합니다. 따라서 운영체제는 과거의 실행 시간 데이터를 기반으로 예측하는 방식으로 스케줄링 결정을 내립니다. (지수적 평균 사용)
    - 지수적 평균 = 최근 값일수록 더 큰 가중치를 부여하고, 오래된 값일수록 점점 덜 중요하게 반영하는 방식의 평균 계산법
- **선점/비선점에서 존재할 수 없는 상태가 있을까요?**
    
    선점형 스케줄링에서는 Running → Ready와 같은 상태 전이가 존재하지만, 비선점형 스케줄링에서는 CPU를 명시적으로 양보하지 않는 한, 이러한 상태 전이가 발생하지 않습니다. 따라서 비선점형에서는 Ready 상태로 되돌아오는 전이가 사실상 존재하지 않을 수 있으며, CPU 점유는 오직 프로세스의 종료나 I/O 요청 등 자발적인 조건에 의해 해제됩니다.
    
- **싱글 스레드 CPU 에서 상시로 돌아가야 하는 프로세스가 있다면, 어떤 스케쥴링 알고리즘을 사용하는 것이 좋을까요? 또 왜 그럴까요?**
    - 응답성 보장과 우선순위 처리가 중요하다
    - 따라서 항상 실행되어야 하는 특정 프로세스가 존재한다면, 우선순위 기반 스케줄링(Priority Scheduling) 기반 방식을 이용하거나. MLFQ 방식을 사용할 수 있다.
- **타 스케쥴러와 비교하여, Multi-level Feedback Queue는 어떤 문제점들을 해결한다고 볼 수 있을까요?**
    
    고정된 우선순위 대신 프로세스의 행동 양식에 따라 동적으로 우선순위를 조정합니다. 덕분에, SJF가 가진 "실행 시간 예측의 어려움", Priority Scheduling이 가진 "기아(starvation) 문제" 등을 효과적으로 해결할 수 있습니다.
    
- **FIFO 스케쥴러는 정말 쓸모가 없는 친구일까요? 어떤 시나리오에 사용하면 좋을까요?**
    
    단순하고 구현이 매우 쉬운 알고리즘으로, 일정한 작업 패턴을 가진 시스템에서는 충분히 유용할 수 있습니다. 특히 작업 시간이 비슷한 배치 처리 시스템에 유용합니다.
    
- **우리는 스케줄링 알고리즘을 "프로세스" 스케줄링 알고리즘이라고 부릅니다. 스레드는 다른 방식으로 스케줄링을 하나요?**
    - 실제로 CPU 입장에서 스케줄링 단위는 스레드(Thread)입니다. 즉, 우리가 흔히 말하는 "프로세스 스케줄링"은 내부적으로는 해당 프로세스의 실행 중인 스레드를 스케줄링하는 것으로 이루어집니다.
    - 각 스레드는 독립적인 PC(Program Counter), 레지스터, 스택을 가지며, 운영체제는 이들 각각을 CPU에 할당합니다.
    - 따라서 현대 OS에서는 스레드 스케줄링이 곧 프로세스 스케줄링이라고 봐도 무방합니다.
- **유저 스레드와 커널 스레드의 스케줄링 알고리즘은 똑같을까요?**
    - 운영체제의 스케줄러가 사용하는 스케줄링 알고리즘은 기본적으로 커널 스레드에 적용됩니다. 커널 스레드는 운영체제가 직접 인식하고 관리하는 실행 단위이기 때문에, 우선순위 기반, 라운드 로빈, MLFQ 등 OS가 채택한 프로세스/스레드용 스케줄링 알고리즘을 그대로 적용받습니다.
    - 반면, 유저 스레드는 운영체제가 직접 인식하지 못하기 때문에, 이들끼리의 스케줄링은 사용자 공간의 라이브러리 또는 런타임이 별도로 관리합니다. 따라서 유저 스레드에는 운영체제의 커널 스케줄링 알고리즘이 적용되지 않고, 예를 들어 협력적(cooperative) 스케줄링, 간단한 라운드 로빈, 혹은 라이브러리 정의 스케줄링처럼 별도의 경량 알고리즘이 사용될 수 있습니다.

- **뮤텍스와 세마포어 모두 커널이 관리하기 때문에, Lock을 얻고 방출하는 과정에서 시스템 콜을 호출해야 합니다. 이 방법의 장단점이 있을까요? 단점을 해결할 수 있는 방법은 없을까요?**
    - 뮤텍스(Mutex)와 세마포어(Semaphore)는 커널 수준에서 관리되는 동기화 객체이므로, 락을 얻거나 해제할 때마다 시스템 콜이 필요합니다. 이는 사용자 공간에서 커널 공간으로의 전환이 발생하기 때문에 성능상 불리합니다.
    - 하지만 그만큼 신뢰성과 일관성은 높아지고, 스레드 간 충돌 방지나 잠금 보장이 확실하게 수행됩니다. 위의 단점을 해결하기 위해 User Space 락을 사용할 수 있습니다.
    - 예를 들어, Java에서는 ReentrantLock이 내부적으로 CAS(Compare-And-Swap) 기반의 사용자 공간 락을 먼저 시도하고, 실패 시에만 커널 락으로 넘어갑니다. 이러한 방식은 커널 진입을 최소화해 낮은 지연 시간과 높은 처리량을 보장할 수 있습니다.
- **DeadLock 조건 중 3가지만 충족하면 왜 Deadlock 이 발생하지 않을까요?**
    
    데드락의 네 가지 조건이 모두 만족되지 않으면 반드시 빠져나갈 틈이 존재합니다. 예를 들어 상호 배제 + 점유와 대기 + 비선점이 모두 성립한다고 하더라도, 순환 구조가 없다면 언젠가는 교착 상태가 풀린다는 점을 논리적으로 알 수 있습니다.
    
- **왜 현대 OS는 Deadlock을 처리하지 않을까요?**
    
    데드락을 실시간으로 탐지하고 복구하는 데 드는 비용과 복잡성이 매우 크기 때문입니다. 많은 시스템에서는 데드락이 실제로 발생할 가능성이 낮고, 발생하더라도 수동 재시작이나 타임아웃으로 충분히 대응 가능하다고 판단합니다.
    
- **Lock Free와  Wait free를 비교해 주세요.**
    
    Lock-Free 안에 Wait-Free가 포함된 형태! (락을 사용하지 않고 동기화)
    
    Lock-Free는 시스템에 여러 스레드가 존재할 때, 그 중 적어도 하나는 항상 작업을 완료할 수 있음을 보장하는 동기화 방식입니다. 즉, 전체 시스템이 멈추는 일은 없지만, 개별 스레드는 굶을 수도 있습니다. (CAS)
    
    Wait-Free는 모든 스레드가 지연 없이 작업을 반드시 완료할 수 있다는, 더 강한 보장을 제공합니다. 따라서 Wait-Free는 Lock-Free보다 더 높은 안정성을 보장하지만, 설계와 구현이 복잡하고 비용이 많이 듭니다. 실무에서는 대부분 Lock-Free가 현실적인 타협점으로 사용됩니다. (만약 CAS가 루프 없이 단일 구조라면!)
    
- **Volatile 키워드는 어떤 의미가 있나요?**
    
    Java에서 volatile 키워드는 변수의 값을 CPU 캐시에 저장하지 않고, 항상 메인 메모리에서 읽고 쓰도록 강제하는 키워드입니다. 이를 통해 멀티스레드 환경에서 가시성(visibility) 문제를 해결할 수 있습니다. 일반적으로 스레드는 변수 값을 캐시에 보관하고 사용하기 때문에, 다른 스레드가 변경한 값을 즉시 알지 못할 수 있습니다. volatile을 사용하면 이 문제를 방지할 수 있으며, 값이 바뀌었음을 모든 스레드가 즉시 감지할 수 있게 됩니다. 하지만 volatile은 원자성(atomicity)은 보장하지 않으므로, 복합 연산에는 AtomicInteger나 synchronized 같은 방법을 함께 사용해야 합니다.
    
- **싱글코어가 아니라 멀티코어라면, 어떻게 동기화가 이뤄질까요?**
    - Mutex를 사용했을 때 멀티코어 환경에서도 동기화가 이루어진다. 그 이유는 Mutex가 **커널 수준에서 관리되는 전역 락**이기 때문이다.
    - 락을 `lock()` 할 때, 커널 또는 라이브러리가 내부적으로 **메모리 배리어(memory barrier)** 를 사용하여 동기화를 보장한다.
    - 메모리 배리어는 CPU의 명령어 실행 순서를 제어하는 기술로 메모리 배리어는 캐시와 메인 메모리 간의 데이터를 동기화시키는 역할을 한다!
        - 멀티코어 시스템에서는 CPU가 성능 최적화를 위해 명령어 순서를 바꾸거나, 캐시에 있는 값을 메인 메모리에 늦게 반영할 수 있기 때문
        - 락을 획득할 때: 이전의 모든 메모리 읽기/쓰기 완료될 때까지 대기
        - 락을 해제할 때: 이후에 수행될 메모리 연산 락 해제 후로 미룸
    
    | **mutex** | 접근을 막는 **커널 수준 락**. 다른 스레드는 커널이 막아서 접근 불가 |
    | --- | --- |
    
    | **memory barrier** | CPU 간 **명령어/메모리 순서 보장**. 캐시-메모리 간 동기화 강제 |
    | --- | --- |

- **Thread Safe 하다는 것은 어떤 의미인가요?**
    
    Thread Safe하다는 것은 여러 스레드가 동시에 같은 자원에 접근하더라도, 그 자원의 상태가 일관되게 유지되는 것을 의미합니다. 다시 말해, 다중 스레드 환경에서 특정 메서드나 객체가 동기화 문제 없이 정상적으로 동작한다면 그것을 Thread Safe하다고 합니다.
    
- **Thread Safe 를 보장하기 위해 어떤 방법을 사용할 수 있나요?**
    
    Thread Safe를 보장하기 위해 여러 가지 방법이 존재합니다. 가장 일반적인 방법은 동기화(synchronization)를 통한 접근 제어입니다. Java에서는 `synchronized` 키워드나 `ReentrantLock`을 사용하여 임계 구역에 하나의 스레드만 진입하도록 보장할 수 있습니다. 그 외에도 Atomic 클래스(예: `AtomicInteger`)를 활용한 CAS 방식, ThreadLocal을 통한 데이터 분리, 불변 객체(Immutable Object)의 사용, 메시지 큐 기반의 병렬 처리 등이 있습니다. 상황에 따라 적절한 동기화 전략을 선택하는 것이 중요합니다.
    
- **Peterson's Algorithm 이 무엇이며, 한계점에 대해 설명해 주세요.**
    
    ```java
    boolean[] flag = new boolean[2]; // 각 스레드가 '나 들어갈 거야!'라고 선언
    int turn = 0; // 누구 차례인지
    
    //실제 동작
    flag[i] = true;         // 나 들어가고 싶어!
    turn = j;               // 그런데 일단 너 먼저 해!
    while (flag[j] && turn == j)
        ;                   // 대기 (상대방이 먼저 하도록 양보함)
    
    // → 여기서 임계 구역 진입
    
    // 임계 구역 끝나고 나서
    flag[i] = false;
    ```
    
    - 두 스레드가 동시에 들어가려 하더라도 `turn` 변수로 양보함
    - 한 쪽만 진입 가능함 (서로 "너 먼저 해!" 하는 겸손 배틀로 조절됨)
    - 코드를 한 줄씩 순차적으로 실행된다는 가정 하에만 안전하게 동작한다.
    - 하지만, 현대 컴퓨터 시스템은 성능 향상을 위해 CPU 수준에서의 명령 재배치가 이루어 질 수 있다. (각 줄이 종속성이 없다고 판단하여) → 한계점
- **Thread Safe를 구현하기 위해 반드시 락을 사용해야 할까요? 그렇지 않다면, 어떤 다른 방법이 있을까요?**
    - **원자적 연산(Atomic Operations)**
        
        현대의 많은 프로그래밍 언어는 원자적 연산을 제공하며, 원자적 연산은 스레드 안전한 연산입니다.
        
        이런 연산은 여러 스레드가 값을 읽거나 업데이트할 때 서로 간섭하지 못하도록 보장합니다.
        
    - **Lock-Free and Wait-Free Algorithms**
        
        이러한 고급 알고리즘은 구현은 복잡하지만 락을 사용하지 않고 동시성을 달성할 수 있습니다.
        
        - ConcurrentLinkedQueue → 내부에서 head, tail 포인터를 CAS로 조작함
            - Lock-Free (충돌 시 Starvation 가능)
        - AtomicInteger.getAndIncrement() → 내부적으로 한 번의 CAS 연산을 수행
            - Wait-Free (연산이 끝나는 것이 보장됨)
    - **메시지 패싱(Message Passing)**
        
        데이터를 직접 공유하는 대신 스레드 간에 메시지 패싱을 통해 통신할 수 있습니다. 이로써 공유 리소스와 락이 필요하지 않으며, 각 스레드는 자체 데이터 복사본에서 작업합니다.
        
        - 스레드(또는 프로세스)들이 직접 메모리를 공유하지 않고,
        - 각자 데이터를 가지고 있다가, 필요할 때 “메시지”를 통해서만 서로 통신하는 방식 (보통 스택에 갖고 있다.)
- **Thread Pool, Monitor, Fork-Join에 대해 설명해 주세요.**
    - Thread Pool은 제한된 수의 스레드를 미리 생성해두고 작업 큐에 들어오는 작업들을 스레드에게 할당하는 방식입니다. 새로운 스레드를 생성하는 오버헤드를 줄이고, 자원 낭비를 방지할 수 있는 효율적인 구조입니다. Java에서는 ExecutorService가 대표적인 예입니다.
    - Monitor는 하나의 객체 내부에서 임계 구역에 대한 접근 제어와 조건 변수의 동기화까지 제공하는 추상화된 구조입니다. Java에서는 synchronized, wait(), notify() 메서드를 통해 Monitor 개념이 구현되어 있습니다.
    - Fork-Join은 하나의 큰 작업을 여러 개의 작은 작업으로 쪼개고, 병렬로 처리한 후 결과를 다시 합치는 병렬 처리 프레임워크입니다. Divide and Conquer 패턴을 기반으로 하며, Java 7부터 도입된 ForkJoinPool이 대표적입니다. 스레드마다 분할된 작업을 처리하고, 먼저 작업을 처리한 스레드는 Work Stealing 알고리즘을 통해 스레드 간 작업 분산을 효율적으로 처리합니다.
- **Thread Pool을 사용한다고 가정하면, 어떤 기준으로 스레드의 수를 결정할 것인가요?**
    
    CPU 바운드 작업의 경우, 가능한 한 CPU를 최대한 활용하는 것이 중요하므로, 스레드 수는 일반적으로 CPU 코어 수와 같거나 그보다 조금 많은 정도로 설정합니다. (프로세스가 CPU를 집중적으로 사용한다는 가정)
    
    I/O 바운드 작업의 경우, 스레드가 대기 상태에 있는 시간이 많기 때문에, 더 많은 수의 스레드를 활용해 병렬성을 높일 수 있습니다.

- **캐시 메모리 및 메모리 계층성에 대해 설명해 주세요.**
    
    캐시 메모리는 CPU와 주기억장치(메인 메모리) 사이에 위치하여, 속도가 느린 메인 메모리 접근을 줄이기 위해 자주 사용되는 데이터를 임시로 저장하는 고속 메모리입니다. 컴퓨터 시스템은 CPU → 캐시 → 메인 메모리 → 보조 기억장치(HDD/SSD)의 형태로 계층적인 메모리 구조(Hierarchy) 를 가지며, 상위 계층일수록 속도가 빠르고 용량은 작으며, 하위 계층일수록 속도는 느리지만 용량이 큽니다. 이러한 구조를 통해 성능과 비용 사이의 균형을 이룹니다.
    
- **L1, L2, L3 캐시에 대해 설명해 주세요.**
    - L1 캐시는 일반적으로 CPU 칩안에 내장되어 데이터 사용/참조에 가장 먼저 사용된다. L1 캐시는 보통 8~64KB 정도의 용량이다. (듀얼 코어 CPU에서는 각 코어 안에 L1이 내장되어 있고 L2를 공유하는 것이 일반적이다.)
    - L2 캐시 메모리는 용도와 역할은 L1 캐시와 비슷하지만 속도는 그보다 느리다. 일반적으로 64KB~4MB 정도가 사용된다.
    - L3 캐시 메모리는 대부분 CPU에 없다. L2 캐시로 충분히 커버할 수 있기 때문이다. 코어 i7에는 8MB의 L3 캐시가 있다. L1/L2 캐시 메모리 정도만 CPU 성능에 직접적인 영향을 미치기에 L3 캐시는 크게 신경쓰지 않는것이 일반적인 추세다.
- **캐시에 올라오는 데이터는 어떻게 관리되나요?**
    
    캐시는 데이터를 캐시 라인(Cache Line) 단위로 저장하며, 일반적으로 하나의 캐시 라인은 64바이트 크기입니다. CPU는 메모리에 접근할 때 단일 주소만이 아니라, 그 주소가 포함된 전체 캐시 라인을 메모리에서 불러와 캐시에 저장합니다. 이는 공간 지역성을 활용하여 향후 인접 데이터 접근 시 성능을 높이기 위함입니다.
    
- **캐시간의 동기화는 어떻게 이루어지나요?**
    
    멀티코어 시스템에서는 각 코어가 자체 캐시를 가지고 있기 때문에, 동일한 메모리 영역을 여러 코어가 다르게 가지고 있을 수 있습니다. 이 경우 캐시 일관성(Cache Coherency) 문제가 발생합니다. 이를 해결하기 위해 CPU는 하드웨어 수준에서 캐시 일관성 프로토콜(Coherency Protocol) 을 적용합니다.
    
    대표적인 프로토콜로는 MESI(MODIFIED, EXCLUSIVE, SHARED, INVALID) 프로토콜이 있습니다. MESI는 각 캐시 라인의 상태를 정의하고, 데이터의 변경이나 접근에 따라 상태 전이를 일으켜 다른 캐시에 있는 동일한 데이터가 잘못된 값을 참조하지 않도록 합니다. 예를 들어 한 코어가 데이터를 수정하면, 다른 코어의 해당 캐시 라인은 무효화(INVALID)되고, 이후 접근 시 다시 메모리 또는 최신 캐시에서 데이터를 받아오게 됩니다.
    
    이러한 동기화는 보통 버스(통로) 감시(Snooping) 방식을 통해 이루어지며, 캐시 간의 통신을 통해 실시간으로 일관성을 유지합니다. 모든 캐시가 이 버스를 감시하면서, "누가 어떤 주소에 쓰려고 하는구나" 를 실시간으로 알 수 있습니다.
    
- **캐시의 공간 지역성은 어떻게 구현될 수 있을까요? (힌트: 캐시는 어떤 단위로 저장되고 관리될까요?)**
    
    캐시는 일반적으로 캐시 라인(Cache Line) 단위로 데이터를 저장하며, 하나의 캐시 라인은 보통 64바이트 정도입니다. 이는 공간 지역성(spatial locality) 을 활용하기 위함입니다.
    
    - 캐시 라인(Cache Line): 캐시가 데이터를 불러올 때 메모리에서 가져오는 최소 단위야. 보통 64바이트로 정해져 있다.
    - CPU가 어떤 메모리 주소 `0x1000`에 접근했다고 가정했을 때, 캐시 컨트롤러는 이 주소 하나만 가져오는 게 아니라, 이 주소가 포함된 전체 캐시 라인(예: `0x1000~0x103F`까지, 총 64바이트) 를 한꺼번에 캐시에 올린다.

- **File Descriptor와, File System에 에 대해 설명해 주세요.**
    - **File Descriptor**
        - 운영체제에서 파일, 소켓, 파이프 등 다양한 I/O 자원을 구분하기 위해 사용하는 정수값
        - 리눅스에서는 0: stdin, 1: stdout, 2: stderr가 기본 FD로 예약되어 있음
        - 프로세스가 실행 중에 파일을 열면 커널은 해당 프로세스의 File Descriptor 숫자 중에 사용하지 않는 가장 작은 값을 할당해줌
        - 그 다음 프로세스가 열려있는 파일에 시스템 콜을 이용해 접근할 때, File Descriptor 값을 이용해 파일을 지칭할 수 있음
    - **File System(파일 시스템)**
        - 컴퓨터에서 파일/자료를 쉽게 찾을수 있도록 유지/관리하는 방법
        - 디스크에 저장된 데이터를 계층적(트리 구조) 으로 관리하고, 파일 이름 → 실제 저장 위치(블록)로 매핑해주는 시스템
        - 메타 영역: 파일 데이터의 데이터가 저장된 영역 (파일 이름, 위치, 크기, 유형 등)
        - 데이터 영역: 실제 데이터가 기록된 영역
- **I-Node가 무엇인가요?**
    - index node의 줄임말로, 파일 시스템에서 파일이나 디렉토리의 메타데이터를 저장하는 데 사용됩니다.
    - 메타데이터에는 파일의 소유자, 그룹, 권한, 크기, 생성 시간, 수정 시간, 마지막 접근 시간 등의 정보가 포함됩니다.
    - inode는 파일명은 저장하지 않고, 디렉토리 엔트리의 파일명과 매핑됩니다.
        - 디렉토리: hello.txt → inode #12345`
        inode #12345 → 실제 파일 정보 + 블록 위치
    - inode에는 실제 파일 데이터가 저장된 디스크 블록의 주소들이 들어 있습니다.
    - 하지만 모든 블록 주소를 직접 다 들고 있지는 않고,다단계 포인터 구조를 사용
        - 처음엔 직접 넣고 (Direct Block)
        - 파일이 커서 하나의 inode에 들어가지 않는다면, 간접 포인터를 통해 더 많은 주소를 다단계로 연결하는 것
- **FIle Descriptor와 i-Node는 무슨 관계인가요?**
    - **FIle Descriptor**
        - FIle Descriptor는 특정 프로세스가 `open()` 과 같은 함수를 호출할 때, 운영체제가 해당 프로세스에게 부여하는 파일 구분 식별자입니다.
        - 운영체제는 각 프로세스마다 File Descriptor Table이라는 테이블을 만들어서 그 프로세스가 열고 있는 파일들을 번호(FD: 0, 1, 2, 3, …) 로 관리합니다.
        - 테이블은 커널 공간의 `task_struct` 에 저장되는데, 직접적으로 저장된게 아니라  FD의 포인터만 저장해서 여러 스레드들이 FD를 공유할 수 있다.
        - 즉, FD는 전역(global) 한 숫자가 아니라, 프로세스 로컬(local) 한 숫자이고, 프로세스가 종료되는 겅유 사라집니다.
    - **i-Node**
        - 운영체제에서 실제로 디스크 내부와 매핑하기 위한 메타 데이터입니다.
        - 파일을 생성할 때 만들어집니다.
        - FD의 엔트리는 파일 테이블을 가리기키고 있고, 파일 테이블에는 i-Node 구조체를 가리키는 포인터 가 있습니다. 해당 i-Node 구조체의 정보를 통해 실제 디스크에 접근하게 됩니다.
- **프로그래밍 언어 상에서 제공하는 파일 관련 함수 (Python - open(), Java - BufferedReader/Writer 등)은, 파일을 어떤 방식으로 읽어들이나요?**
    - 대부분의 언어에서 제공하는 고수준 I/O 함수들(ex. Python의 open(), Java의 BufferedReader)은 내부적으로 운영체제의 시스템 콜(read(), write(), open() 등) 을 호출한다.
    - 예를 들어 Python에서 open("file.txt")를 호출하면, 내부적으로는 OS에게 시스템 콜 open()을 요청하고, File Descriptor를 받는다.
    - 이후 read() 등을 호출하면 운영체제는 해당 FD에 연결된 I-Node를 조회하고, 디스크 블록에서 내용을 읽어 메모리로 가져온다.
    - Java의 BufferedReader는 이 과정에서 버퍼링을 추가로 수행하여, 많은 데이터를 한꺼번에 읽어 들이고 성능을 높인다.
    - 즉, 프로그래밍 언어는 파일 I/O를 쉽게 쓸 수 있게 감싸줄 뿐, 결국은 운영체제 커널을 통해 파일 시스템과 상호작용하게 된다.
- **저널링(Journaling)에 대해 설명해주세요**
    
     일반적인 파일 시스템에서는 파일을 변경하는 작업이 중간에 끊기면 메타데이터와 실제 데이터가 불일치하게 되어 손상이 발생할 수 있습니다. 하지만 저널링 시스템은 모든 변경 작업을 실제로 수행하기 전에 로그(저널)에 기록합니다. 이 로그는 일반적으로 일반적인 파일/디렉터리가 저장되는 데이터 블록(1KB) 영역과 물리적으로 분리된 저널 블록에 존재하며, 파일이나 디렉토리 변경 사항을 일종의 트랜잭션처럼 다루어, 시스템이 재부팅되면 이 로그를 기준으로 중단된 작업을 복원하거나 되돌릴 수 있게 됩니다.
    
- **파일 시스템 마운트(Mount)에 대해 설명해주세요.**
    
    마운트(Mount)는 운영체제가 하나의 통합된 디렉토리 구조를 제공하기 위해 사용하는 기법으로, 물리적으로 분리된 파일 시스템을 특정 디렉토리 경로에 연결하는 작업입니다. 예를 들어, 외장 하드디스크나 USB를 연결하면 `/mnt/usb` 같은 디렉토리에 해당 장치의 파일 시스템이 붙게 됩니다. 이 과정은 사용자가 직접 `mount` 명령어를 통해 수동으로 할 수도 있고, 시스템이 자동으로 수행할 수도 있습니다. 
    
- **디스크 할당 방식에 대해 설명해주세요.**
    
    디스크 블록 할당 방식은 파일을 저장할 때 데이터를 디스크에 어떤 순서로 배치할지를 결정하는 전략입니다. 
    
    - 연속 할당은 하나의 파일이 디스크 상에 연속된 블록에 저장되는 방식으로, 접근 속도가 빠르고 구현이 간단하지만, 외부 단편화가 발생할 수 있고 큰 파일을 위해 충분히 큰 연속 공간을 찾기 어려울 수 있습니다.
    - 연결 할당은 각 블록이 다음 블록의 주소를 저장하는 방식으로, 단편화 문제는 없지만 랜덤 접근이 비효율적입니다.
    - 인덱스 할당은 별도의 인덱스 블록을 사용하여 모든 데이터 블록의 주소를 저장하는 방식으로, 빠른 접근과 효율적인 공간 관리를 가능하게 해 ext4와 같은 현대적인 파일 시스템에서 널리 사용됩니다. (이 인덱스 블록의 역할을 아이노드(inode)가 수행)
- **I/O 멀티플렉싱에 대해 설명해 주세요.**
    
    I/O 멀티플렉싱은 하나의 스레드(또는 프로세스)가 여러 개의 I/O 작업을 동시에 기다릴 수 있도록 하는 기술입니다.
    즉, 단일 스레드가 여러 파일 디스크립터(FD)를 동시에 감시하다가, 어떤 FD가 읽기/쓰기 가능한 상태가 되면 해당 작업을 수행하는 방식입니다.
    
    이 방식은 대표적으로 select, poll, 그리고 epoll(리눅스)이 있습니다.
    
    - select와 poll은 매번 감시 대상 전체를 커널에 전달해야 하므로 성능에 제한이 있고,
    - epoll은 감시 대상을 등록해놓고 이벤트 기반으로 처리하기 때문에 대규모 연결 처리에 효율적입니다.
    
    이러한 멀티플렉싱 방식은 블로킹 I/O를 사용하는 것보다 자원 효율성이 높고,
    멀티스레딩 없이도 다수의 클라이언트를 처리할 수 있어 서버 개발에서 자주 사용됩니다. 대표적으로 Node.js나 Nginx가 이 모델을 채택하고 있습니다.
    
- **논블로킹 I/O를 수행한다고 하면, 그 결과를 어떻게 수신할 수 있나요?**
    
    논블로킹 I/O란, 시스템 콜이 즉시 반환되어 데이터가 준비되지 않았더라도 기다리지 않는 방식입니다. 이때 결과를 수신하는 방법은 일반적으로 폴링(Polling) 또는 이벤트 기반 콜백(Event-driven)으로 나뉩니다.
    
    - **폴링(Polling)**
        - 주기적으로 read() 또는 recv() 같은 호출을 반복해서 직접 데이터가 들어왔는지 확인합니다.
        - CPU를 낭비할 수 있으므로 효율은 낮습니다.
    - **I/O 멀티플렉싱과 결합 (select/poll/epoll)**
        - 논블로킹 소켓과 함께 select나 epoll을 사용하면, 커널이 읽기/쓰기가 가능한 이벤트가 발생했을 때만 알려줘서, 그때 데이터를 읽을 수 있습니다.
        - 불필요한 폴링 없이 효율적인 처리가 가능합니다.
    - **이벤트 루프 + 콜백**
        - 고수준에서는 이벤트 루프 기반 라이브러리에서 논블로킹 작업이 완료되면 콜백 함수를 실행하게 하여 결과를 전달합니다.
        - I/O 멀티플렉싱의 경우 프로그래머가 명시적으로 제어해야 하지만, 이벤트 루프의 경우에는 이벤트 루프 라이브러리가 자동으로 해주는 차이가 있음
    
    즉, 논블로킹 I/O는 단독으로는 결과 수신에 비효율적일 수 있고, I/O 멀티플렉싱과 함께 사용함으로써 효과적인 이벤트 기반 처리가 가능해집니다.
