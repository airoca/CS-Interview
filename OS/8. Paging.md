- **페이징이 무엇인지 설명해주세요.**
    
    운영체제에서 페이징(Paging)은 가상 메모리(Virtual Memory) 관리 기법 중 하나로, 프로세스의 논리 주소 공간(Logical Address Space)을 고정 크기의 페이지(Page)로 나누고, 물리 메모리(Physical Memory)는 동일한 크기의 프레임(Frame)으로 나누어 관리하는 방식입니다. 외부 단편화 문제를 해결하기 위해 등장했습니다.
    
    - **페이지(Page)**
        - 프로세스의 가상 주소 공간을 일정 크기로 나눈 단위
    - **프레임(Frame)**
        - 물리 메모리를 페이지와 같은 크기로 나눈 단위
    - **페이지 테이블(Page Table)**
        - 각 페이지가 물리 메모리의 어느 프레임에 있는지를 저장한 테이블

- **페이징의 주소 변환 과정을 설명해주세요.**
    
    ![image.png](attachment:e7d33a1e-c2ef-4e42-b329-c84c94bd8e5c:image.png)
    
    - **VPN:** 몇 번째 페이지인가? → 페이지 테이블 인덱스로 사용
    - **offset:** 해당 페이지 내에서의 위치 → 그대로 물리 주소에 포함됨
    - 32비트 시스템에서 페이지 크기는 2^12 = 4KB이다.
        - 페이지 번호: 상위 20비트
        - 페이지 오프셋: 하위 12비트
    - **변환 과정**
        - 가상 주소 `0x12345678` 분해
            - 상위 20비트 → PFN: `0x12345`
            - 하위 12비트 → offset: `0x678`
        - 운영체제는 **페이지 번호에 해당하는 엔트리**를 **페이지 테이블**에서 찾음
            - Page Table[0x12345] = 0xABC
        - 물리 주소를 계산한다.
            - 물리 주소 = [프레임 번호(상위)] + [페이지 오프셋(하위)]
        - 실제 주소 변환은 MMU(Memory Management Unit)가 수행한다.
            - MMU(Memory Management Unit)는 CPU에 붙어 있는 하드웨어 장치로, CPU가 사용하는 "가상 주소"를 실제 "물리 주소"로 바꿔주는 역할만을 수행한다.
            - 따라서, 주소 변환 자체는 MMU라는 하드웨어가 처리하고, 운영체제는 그 변환에 필요한 정보를 "미리 준비하고 관리"하는 역할을 한다.
            - TLB(Translation Lookaside Buffer)라는 캐시가 있어서, 자주 쓰는 매핑은 빠르게 처리할 수 있다.

- **페이지 테이블이 무엇인지 설명해주세요.**
    
    가상 주소의 “페이지 번호”가 물리 메모리의 “프레임 번호”로 어떻게 매핑되는지를 기록해둔 게 페이지 테이블이다.
    
    PTE(Page Table Entry)는 페이지 테이블 내부의 각각의 항목으로, 아래의 정보들을 포함하고 있다.
    
    - **Valid Bit**
        - 해당 변환이 유효한지(실제 사용되는 공간인지) 여부
    - **Protection Bit**
        - 페이지가 읽기, 쓰기 또는 실행 가능한지 여부
    - **Present Bit**
        - 페이지가 메모리, 또는 디스크(Swap Out)에 있는지 여부
    - **Dirty Bit**
        - 페이지가 메모리에 들어온 후 수정되었는지 여부
    - **Reference Bit (Accessed Bit)**
        - 페이지가 접근되었는지 여부 (Swap에 사용)

- **페이징의 단점에 대해 설명해주세요.**
    
    페이징의 단점은 페이지 테이블을 통해 가상 주소를 물리 주소로 변환하기 때문에, 주소 변환 과정에서 추가적인 오버헤드가 발생할 수 있고, 페이지 테이블이 커질 경우 메모리 공간을 많이 차지할 수 있다는 점이다.
    
    Page Table은 크기가 너무 크기 때문에 CPU 내부에 정보를 저장할 수 없다. 따라서 Page Table에 접근하기 위해 물리 메모리(RAM)에 접근이 필요하며, 이 과정에서 오버헤드가 발생한다.
    

- **TLB에 대해 설명하고, 왜 필요한지 설명해주세요.**
    
    TLB는 최근에 사용된 페이지 테이블 매핑 정보를 CPU 내부에 캐시(Cache)하여, 주소 변환을 빠르게 처리할 수 있도록 돕는다. 페이지 테이블을 CPU 내부에 전부 저장할 수는 없으니, 자주 사용되는 페이지의 매핑 정보만 CPU 내부에 캐시하는 것이다.
    
    데이터/명령어를 저장하는 L1, L2, L3 캐시와 별도로 TLB를 위한 캐시 공간이 존재
    
    이 때 원하는 매핑이 TLB에 존재하는 상황을 TLB Hit, 존재하지 않는 상황을 TLB Miss라고 한다.
    

- **TLB Miss는 어떻게 처리되나요?**
    - **Hardware-managed**
        - CISC 아키텍처에서는 TLB Miss를 하드웨어가 전적으로 처리한다.
        - MMU가 직접 페이지 테이블을 탐색해서 TLB miss를 처리하는 방식
        - 하드웨어는 페이지 테이블이 메모리 어디에 위치하는지 정확히 알고 있어야 하며, 이를 통해 페이지 테이블을 탐색하여 적절한 페이지 테이블 항목(PTE)을 찾아 원하는 매핑을 추출한다.
        - 이후, 해당 매핑을 TLB에 업데이트하고, 명령어를 재실행하여 주소 변환을 완료한다.
        - Intel x86 CPU가 Hardware-managed TLB의 대표적인 예시인데, "Multi-Level Page Table"이라는 개념을 추가로 사용한다.
    - **Software-managed**
        - RISC 아키텍처에서는 보 TLB Miss를 소프트웨어가 관리한다.
        - MMU가 TLB miss를 감지하면 예외(Trap)을 발생시켜 운영체제가 직접 페이지 테이블을 탐색하고, TLB에 값을 채워주는 방식
        - 트랩 핸들러는 운영 체제 내의 코드로, TLB Miss가 발생한 경우 이를 처리하는 데 필요한 작업을 수행한다. 여기에는 페이지 테이블을 조회하고, TLB에 새로운 변환 정보를 삽입하며, 명령어를 재시작하는 등의 작업이 포함된다.

- **요구 페이징(Demand Paging)이 무엇인지 설명해주세요.**
    
    요구 페이징(Demand Paging)은 프로그램 실행 시작 시에 프로그램 전체를 물리 메모리에 적재하는 대신, 초기에 필요한 것들만 적재하는 전략을 의미합니다. 가상 메모리와 페이지 개념을 활용해 관리됩니다.
    

- **페이지드 세그먼테이션이 무엇인가요?**
    - 두 가지 방법을 합쳐서 내/외부 단편화 문제를 완화
    - 세그먼트 단위로 논리적 구분 + 페이지 단위로 실제 메모리 배치
        - 프로그램은 코드, 데이터, 스택 등 논리적 세그먼트로 나뉘어 있음
        - 각 세그먼트는 다시 페이지 단위(고정 크기 블록)로 나뉨
        - CPU는 가상 주소를 세그먼트 번호 → 페이지 번호 → 오프셋으로 분리
            - 가상 주소 = [세그먼트 번호][페이지 번호][오프셋]
    - **장점**
        - 프로그램은 여전히 코드/데이터/스택 등 논리적 구조로 관리하지만, 세그먼트 전체를 연속된 물리 메모리에 할당하지 않는다는 것이 핵심!
        - 페이지 단위로 나눠서 쪼개서 아무 데나 배치한다.
        - 따라서 외부 단편화를 해소하고, 페이지의 크기 또한 작아져 내부 단편화도 해소할 수 있다.
    - **한계점**
        - CPU가 주소를 변환하려면 2단계를 거쳐야 한다. (메모리 접근 느려짐)
        - 현대 OS는 TLB 등 메모리를 페이지 단위로 통일해서 다루기 때문에 이점이 적다.
        - 페이지 테이블 크기도 커지고, TLB Miss도 늘어난다.
        - 현대  OS는 세그먼트 별로 다른 페이지를 사용하긴 하지만, 페이지드 세그먼테이션 같이 하드웨어적으로 세그먼트 접근을 분류하고 있지는 않다.

- **페이지 테이블의 크기를 줄이기 위한 방법은 무엇이 있을까요?**
    - **단순히 큰 페이지를 할당**
        - 내부 단편화 악화!
    - **Hybrid Approach**
        - 세그먼트별 페이지 테이블 할당
        - 페이지 테이블도 3배로 늘어나는 거 아닌가요? → 아니다
            - 기존에는 비어있는 공간에 대해서도 무조건 테이블 엔트리를 만들어서 페이지 테이블의 크기가 늘어남
            - 하지만 하이브리드 방식에서는 코드/힙/스택으로 나누어 “진짜 사용하는 세그먼트”만 페이지 테이블을 생성한다.
        - 하지만 Heap을 과도하게 할당할 경우 메모리 낭비 문제가 생기고, 세그먼트들 사이에 메모리 공간이 고르게 분포되지 않아 External Fragmentation 문제가 생길 수 있다.

- **Multi-level Page Tables에 대해 설명해주세요.**
    - 페이지 테이블을 트리와 같은 계층 구조로 표현하는 것이다.
    - 페이지 테이블을 여러 층으로 나눠서, 사용 중인 주소 영역에 대해서만 하위 테이블을 동적으로 생성하는 방식이다.
    - **장점**
        - 필요한 만큼만 페이지 테이블 공간을 할당하여 메모리 낭비를 줄일 수 있다.
    - **단점**
        - 주소 접근 단계가 추가되므로, 메모리 엑세스 시간이 늘어난다.
        - 구현이 복잡하다.

- **Swap에 대해 설명해주세요.**
    - 만약 프로세스에서 요구하는 메모리가 현재 남아있는 물리 메모리의 크기보다 크다면 어떻게 해야할까?
    - 일부 데이터를 디스크 공간으로 옮겨서 메모리를 비우는 기술을 Swap이라고 한다.
    - 운영체제는 HDD에 위치한 Swap Space라는 공간을 사용하여, 현재 사용되지 않는 프로세스의 메모리 일부를 하드 디스크와 같은 저장 장치에 임시로 저장한다.

- **페이지 폴트가 무엇인가요?**
    - 현재 메모리에 존재하지 않는 페이지에 접근하려고 한 경우 발생되는 예외(인터럽트)이다.
    - TLB Miss는 Hardware-managed 방식과 Software-managed 방식이 있다고 설명했는데, Page Fault는 무조건 운영체제가 처리하게 된다.
    - 페이지 테이블 자체에 물리 주소 매핑이 없는 상태이기 때문에, 프레임 할당 작업을 직접적으로 수행해야 하기 때문이다! (이는 절대 MMU가 처리 불가능)

- **페이지 교체는 실제로 언제 발생하나요?**
    - 운영체제가 메모리가 완전히 가득 찬 후에 페이지를 교체하여 새로운 페이지를 위한 공간을 확보하는 것은 다소 비현실적이다.
    - 따라서 운영체제는 메모리를 미리 일부 비워 두는 방식으로 더 효율적으로 관리한다.
        - **Swap Daemon**
        메모리 부족이 심각해지기 전에(예방), 메모리 공간을 미리 확보하기 위해 백그라운드에서 실행되는 스레드이다. 이 스레드는 페이지를 교체하여 메모리에 여유 공간을 확보하려고 한다.
        - **Page Daemon**
        메모리 사용량이 너무 높아지면(해소) 실행되는 백그라운드 스레드이다. 해당 스레드 또한 페이지를 교체하여 여유 공간을 확보하려고 한다.

- **페이지 교체 알고리즘의 종류를 설명해주세요.**
    - **OPT (Optimal)**
    가장 먼 미래 동안 사용되지 않을 페이지를 교체한다.(불가능)
    - **FIFO (First-In, First-Out)**
        - 단순히 가장 가장 오래된 페이지를 제거하는 방식이다.
        - Belady’s Anomaly에 따르면, FIFO의 경우 캐시 메모리가 증가했을 때 오히려 Miss가 증가하는 현상이 있다.
    - **Random**
        - 랜덤하게 페이지를 교체하는 방식
    - **LRU, LFU**
        - **LRU(Least Recently Used)** 알고리즘은 가장 오래전에 접근된 페이지를 교체 대상으로 선정한다. 즉, **접근 시간(Recency)**을 기준으로 판단한다. 최근에 사용된 페이지를 다시 사용할 가능성이 높지만, 장기적인 사용 패턴을 고려하기 어렵다.
        - **LFU(Least Frequently Used)** 알고리즘은 페이지의 사용 횟수를 추적하여, 가장 적게 사용된 페이지를 교체 대상으로 선정한다. 즉, **접근 빈도(Frequency)**를 기준으로 판단한다. 장기적인 사용 패턴을 반영할 수 있지만, 추가적인 메모리와 계산이 필요하다.

- **LRU 알고리즘은 어떻게 구현할 수 있을까요?**
    - **Clock Algorithm**
        - 가장 정밀한 방법은 HashMap + Doubly Linked List를 통한 구현이지만, 하드웨어나 커널 수준에서는 비용이 너무 높다는 문제가 있다.
        - 실제 운영체제는 근사 LRU 알고리즘을 사용하는데, 가장 대표적인 예가 바로 Clock 알고리즘이다. 각 페이지에 Reference Bit(참조 비트)를 두고, 시계 바늘이 돌면서 참조되지 않은 페이지를 교체 대상으로 선택한다.

- **Thrashing(쓰레싱)에 대해 설명해주세요.**
    
    Thrashing은 운영체제에서 페이지 교체가 지나치게 자주 일어나면서, 실질적인 작업은 거의 수행되지 않고 대부분의 시간이 페이지 적재와 교체에만 소모되는 현상을 말한다.
    
    *프로세스에서 요구하는 메모리가 현재 남아있는 물리 메모리의 크기보다 큰 경우!*
    
    시스템에 실행 중인 프로세스 수가 너무 많고, 각 프로세스가 필요한 작업 집합(Working Set)이 물리 메모리보다 커질 때 발생한다. 이로 인해 페이지 폴트가 급증하고, 디스크 I/O가 과도하게 발생한다.
    

- **Thrashing 해결 방법을 설명해주세요.**
    - **Working Set**
        - Working Set이란, 특정 시간 동안 프로세스가 자주 참조한 페이지들의 집합
        - 대부분의 프로세스가 특정 페이지만 집중적으로 참조하는 특성을 이용
        - 일정 시간 동안 참조되는 페이지 개수를 파악하고, 그 페이지 수만큼 여분 프레임이 확보되면 그 때 페이지를 메모리에 올리는 알고리즘이다.
        - 확보되지 않으면 해당 프로세스를 일시적으로 중단한다.
    - **Page Fault Frequency**
        - Page Fault 퍼센트의 상한과 하한을 둔다.
        - 상한을 넘으면 프레임의 개수를 늘려서 페이지를 더 많이 할당할 수 있도록 합니다, 하한을 넘으면 지급 프레임 개수를 줄인다.
        - 프로세스 단위로 생각해야 한다! 특정 프로세스에 지급된 프레임이 적어서 Swap이 과도하게 발생하면 더 주고, 너무 발생하지 않으면 뺏어서 부족한 프로세스에게 줄 수 있는 것!
    - **물리 메모리 증가, 알고리즘(LRU, LFU 등) 사용**

- **메모리가 고갈되면 일어나는 현상에 대해 설명해주세요.**
    
    메모리가 고갈되었지만, 프로세스를 실행해야 하기 때문에 Swap이 활발해진다. 따라서 CPU 이용률이 하락하고, OS는 CPU 이용률이 낮으므로 오히려 프로세스를 추가하게 되는 Thrashing 현상이 발생한다. 이를 해소하지 못하면 Out Of Memory 상태로 판단해 중요도가 낮은 프로세스를 강제로 종료하게 한다.
