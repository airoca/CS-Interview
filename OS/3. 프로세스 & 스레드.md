- **프로세스에 대해 설명해주세요.**
    - 컴퓨터에서 실행 중인 프로그램(컴퓨터가 실행할 수 있는 명령어들의 집합)
    - 각각의 프로세스는 독립된 메모리 공간을 할당 받는다.
    - 메모리 공간에 명령어들과 데이터를 가진다.

- **프로세스의 3가지 상태에 대해 설명해주세요.**
    
    프로세스는 아래와 같은 세 가지 상태 중 하나에 있을 수 있다.
    
    - **Running**
        
        프로세스가 현재 프로세서에서 실행되고 있는 상태이다.
        
    - **Ready**
        
        프로세스가 실행될 준비가 되어 있지만, 특정 이유로 인해 운영 체제가 이 시점에 해당 프로세스를 실행하지 않은 상태이다.
        
    - **Blocked**
        
        프로세스가 특정 종류의 작업을 수행한 상태이다. 예를 들어, 프로세스가 I/O 요청을 수행하는 경우, 다른 프로세스가 CPU를 사용할 수 있도록 Blocked 상태가 된다.
        

- **프로세스 생성 과정을 설명해주세요.**
    
    fork()는 프로세스를 "복제"하는 것
    exec()는 현재 프로세스를 "새 프로그램으로 덮어쓰기" 하는 것
    
    - **프로세스 생성**
        - 부모 프로세스로부터 `fork()` , `exec()` 시스템 콜이 수행된다.
        - 코드(Code), 데이터(Data), 스택(Stack), 힙(Heap) 영역을 위한 메모리 공간을 커널이 가상 메모리로 설정해준다.
        - `fork()`의 경우 부모의 주소 공간을 복사한다.
            - `fork()`는 부모 프로세스를 복제하여 자식 프로세스를 생성한다.
            - 하지만 부모의 메모리를 전부 복사하는 것은 비용이 크다.
            - 대부분 `fork()` 직후에는 `exec()`로 새로운 프로그램을 로드하기 때문에 복사가 낭비된다.
            - 따라서 **Copy-On-Write** 방식을 사용한다!
            - COW 방식에서는, `fork()` 과정에서 실제 메모리의 내용을 복사하는 대신, 페이지 테이블만 복사하여 단순히 부모와 같은 메모리 페이지를 가리키도록 한다. (Write 권한은 없음)
            - 만약 실제로 부모 데이터에 접근하는 프로세스였다면, 그제서야 메모리를 복사하는 방식이다.
            - 하지만 이후 `exec()` 을 통해 아예 새로운 프로세스를 수행하는 것이었다면, 자식은 기존 메모리를 쓰지도 않고 새로운 프로세스를 메모리에 로딩하는 것이기 때문에 복사가 아예 일어나지 않게 된다. (페이지 테이블 정보도 물론 아예 변경된다.)
        - 부모의 열려 있던 파일 디스크립터도 복사된다.
            - 파일 디스크립터란, 운영체제가 자원(파일 등)을 식별하기 위해 사용하는 정수 값이다. 파일 디스크립터는 프로세스마다 갖는다.
        - 프로세스 상태를 READY로 설정한다.

- **프로세스 생성 시 `fork` 와 `exec` 을 왜 나눌까요?**
    
    `fork`와 `exec` 을 나눈 이유는, 새 프로세스를 만들고 어떤 동작을 할지 프로그래머가 유연하게 결정할 수 있도록 하기 위해서이다.
    
    부모가 자식을 세밀하게 설정 가능하기 때문에, 자식에서 exec() 전에 환경변수, 파일 디스크립터, 권한, 리다이렉션 등 세팅을 자유롭게 할 수 있다.
    
    ```java
    if (fork() == 0) {
        close(1);                   // stdout 닫기
        open("out.txt", O_WRONLY);  // 표준출력을 파일로 대체
        execvp("ls", args);         // 이제 ls 결과는 out.txt로 감
    }
    ```
    

- **프로세스 종료 과정을 설명해주세요.**
    - 프로세스가 종료 요청 수행
        - `exit` , `main()` 리턴, 예외 등
    - 운영체제가 해당 프로세스의 자원을 정리한다.
        - 열려 있던 파일 디스크립터 연결 해제
        - 프로세스에 할당되었던 메모리 해제
        - IPC 자원(파이프, 세마포어 등) 반납
    - Exit 코드 저장 + 좀비(Zombie) 상태 전환
        - 프로세스가 종료되면 완전히 사라지는 게 아니라, 좀비 프로세스(Zombie) 상태로 남는다.
        - 부모가 종료 상태를 확인할 수 있어야 하기 때문이다. 왜?
        - 부모는 자식의 성공/실패 여부에 따라 다른 행동을 할 수 있기 때문!
        - 운영체제는 프로세스의 종료 코드와 사용 자원 통계 등을 PCB에 남겨둔다.
    - 부모 프로세스에게 시그널을 전달한다.
    - 부모 프로세스가 `wait()` 을 통해 자식의 PCB 정보를 확인하면 자원이 전부 해제된다.

- **프로세스의 종류에 대해 설명해주세요.**
    - **자식 프로세스**
        
        fork로 자식 프로세스를 만든 상태, 부모의 데이터, 힙, 스택, PCB 복사
        
    - **데몬 프로세스**
        
        백그라운드에서 동작하면서 특정한 서비스를 제공하는 프로세스
        
    - **고아 프로세스**
        
        부모 프로세스가 먼저 종료되어 고립된 자식 프로세스
        
        - 고아 프로세스는 init(1)이 자동으로 부모가 됨
            - init이란, 리눅스 시스템이 부팅된 후 가장 먼저 실행되는 사용자 공간(user space)의 프로세스
        - init은 자동으로 `wait()` 호출해서 자식이 좀비가 되는 걸 막아줌
        - 따라서 고아 프로세스는 큰 문제가 되지 않는다.
    - **좀비 프로세스**
        
        자식 프로세스가 종료되었음에도 불구하고 부모 프로세스로부터 작업 종료에 대한 승인을 받지 못한 프로세스
        
        - 자식 프로세스 종료 시 자동으로 `wait()`  호출하게 하여 해결!

- **스레드의 등장 배경에 대해 설명해주세요.**
    - 하나의 프로세스가 동시에 여러 작업을 수행하지는 못한다.
    - 프로세스의 컨텍스트 스위칭은 무거운 작업이다.
        - 프로세스 컨텍스트 스위칭 비용은 스위칭할 때마다 CPU 캐시에 있는 내용을 모두 초기화하고, 새로운 프로세스 정보를 CPU 캐시에 적재해야 하므로 높은 비용이 든다. 반면, 스레드 컨텍스트 스위칭 비용은 스위칭할 때 스레드 간에 공유하는 자원을 제외한 스레드 정보(stack, register)만을 교체하면 되므로 프로세스 컨텍스트 스위칭 비용보다 상대적으로 낮은 것이다.
    - 프로세스끼리 데이터 공유가 까다롭다. (메모리 공간 독립적)
    - 듀얼 코어(하나의 CPU에 두 개의 코어)를 잘 쓰기 어렵다.

- **스레드에 대해 설명해주세요.**
    - 프로세스의 CPU 이용의 기본 단위이다. (unit of execution)
    - 프로세스는 한 개 이상의 스레드를 가질 수 있다.
    - 같은 프로세스의 스레드들끼리 컨텍스트 스위칭은 가볍다.
    - 스레드는 프로세스 내에서 Stack만 할당받으며 Code, Data, Heap 영역을 같은 프로세스 내의 스레드 간에 공유한다.

- **스레드마다 독립적으로 할당하는 2가지에 대해 설명해주세요.**
    
    스레드는 독립적으로 스택 영역과 레지스터를 갖고 있다.
    
    - **독립적으로 스택 영역을 갖는 이유**
        - 스택 영역은 함수의 실행과 관련이 있다.
        - 독립적으로 스택을 갖는다는 것은 곧 독립적으로 함수 호출이 가능하다는 것을 의미한다.
        - 즉, 프로세스 내의 독립적인 실행 흐름을 만들기 위해 쓰레드마다 스택 영역을 갖는다.
    - **독립적으로 레지스터 값을 갖는 이유**
        - 스레드는 독립적인 실행 흐름을 가지는 단위입니다.
        - 따라서 CPU가 스레드를 스위칭할 때는 이전 스레드의 모든 레지스터 값을 저장하고, 복원해야 한다.
        - 따라서 스레드마다 레지스터 값도 다르다.

- **프로세스와 스레드의 차이에 대해 요약해주세요.**
    
    **프로세스**
    
    - 메인 메모리(주기억장치)에 적재되어 실행되는 프로그램을 의미합니다.
    - PCB, code, data, heap, stack 영역을 갖습니다.
    - 프로세스별 각각의 영역을 갖기 때문에 별다른 동기화 작업이 필요하지 않습니다.
    - 프로세스별 각각의 영역을 갖기 때문에 context switching 비용이 큽니다.
    - 프로세스 스레드보다 무겁기 때문에 생성 시간이 더 깁니다.
    - 한 프로세스에서 오류가 생기더라도 다른 프로세스에 영향을 주지 않습니다.
    
    **스레드**
    
    - 한 프로세스 내의 실행 단위, 실행의 흐름을 의미합니다.
    - stack 영역만 별도로 갖고, 나머지 영역(code, data, heap)에 대해서는 해당 스레드를 포함한 프로세스의 자원을 공유합니다.
    - stack 영역 외부의 공유 자원에 대해 접근 시 동기화 작업이 필요합니다.
    - stack 영역 외부를 공유하므로 컨텍스트 스위칭 비용이 적습니다.
    - 스레드는 프로세스보다 가볍기 때문에 생성 시간이 더 짧습니다.
    - 한 스레드에서 오류가 생기면, 나머지 프로세스 내의 쓰레드에 영향을 줄 수 있습니다.

- **PCB와 TCB의 차이에 대해 설명해주세요.**
    - **PCB (Process Control Block)**
        - 프로세스 당 하나 존재
        - 프로세스 ID
        - 프로세스 상태 (Ready, Running 등)
        - 메모리 정보 (코드/데이터/스택의 주소 등)
        - 파일 디스크립터 테이블
        - 페이지 테이블 정보
        - 스레드 리스트 (해당 프로세스의 스레드들이 가리키는 TCB들)
    - **TCB (Thread Control Block)**
        - 하나의 스레드당 하나 존재
        - 스레드 ID
        - 레지스터/PC 값 (문맥 전환용)
        - 스택 포인터 (각 스레드는 독립된 스택을 가짐)
        - 스레드 상태 (Ready, Waiting, Running 등)
        - 스레드 우선순위
        - 해당 스레드가 속한 PCB(=프로세스) 참조
    - 스레드는 실제 실행을 담당하는 단위
    - 프로세스는 자원(메모리, 파일 등)을 소유하는 단위
    - 따라서, 코드, 데이터, 힙, 파일 디스크립터 등은 PCB에 저장된다.
    - TCB는 해당 자원 정보가 필요할 때 PCB를 참조해야 하므로 PCB와 TCB는 연결되어 있다.
        - 프로세스 1개, 스레드 1개
            
            스레드가 Running → Blocked로 바뀌면 → 사실상 프로세스 전체가 멈춘 것과 같음
            → 이때 PCB의 상태도 Blocked로 바뀜
            
        - 프로세스 1개, 스레드 4개
            
            스레드가 모두 Blocked 되면 → PCB도 Blocked
            
            하나라도 Ready면 → PCB는 Ready 상태 유지
            
    - 즉, PCB의 상태는 전체 스레드 상태를 “통합적으로 추상화”한 상태

- **유저 스레드와 커널 스레드의 차이를 설명해주세요.**
    - **유저 스레드**
        - 운영체제가 아닌 사용자 공간(user space)에서 라이브러리 수준에서 직접 관리되는 스레드
        - 하나의 프로세스 안에서 라이브러리가 여러 스레드를 만들어 관리하고, 컨텍스트 스위칭도 라이브러리가 수행한다.
        - 커널 개입 없이 스케줄링 가능하므로, 컨텍스트 스위칭이 훨씬 가볍다.
        - 하지만, 하나가 블로킹(예: I/O)되면 전체 유저 스레드가 멈춤 (커널 입장에선 하나의 프로세스니까)
        - 또한, 커널이 한 프로세스만 인식하므로, 멀티코어 병렬 실행이 불가능하다.
        - 현대 OS는 커널 스레드를 잘 관리하므로 굳이 직접 관리할 필요가 줄어들었다. 따라서 잘 사용되지 않는다.
    - **커널 스레드**
        - 커널이 직접 관리하는 스레드. 각 스레드가 커널에 의해 독립된 실행 단위로 인식된다.
        - 커널이 각 스레드를 별도 실행 단위로 보기 때문에 병렬 처리 가능
        - 한 스레드가 블로킹돼도 다른 스레드 실행 가능
        - 스레드 생성/제거 비용과 컨텍스트 스위칭 비용이 높다.
    - **혼합 모델**
        - 일부 시스템은 유저 스레드를 커널 스레드에 매핑(M:N 방식)해서
        양쪽 장점을 모두 활용하는 방식도 사용한다.
        - `N:1` → 전통 유저 스레드 (예: Java Green Thread)
        - `1:1` → 현대 pthread (Linux, Windows)
        - `M:N` → 일부 스레딩 라이브러리, 예: Solaris threads

- **JVM은 유저 스레드를 사용하나요, 커널 스레드를 사용하나요?**
    - **전통적인 Java Thread (new Thread())**
        - 실제로는 OS에서 pthread_create() 같은 시스템 콜을 호출해서
        - OS 커널이 인식하는 진짜 커널 스레드를 생성함
        - 멀티코어 활용 가능, 독립적인 스케줄링 가능
        - 하지만 무겁고, 수천 개 이상 만들기 어려움
    - **Java 21의 Virtual Thread**
        - **JVM 내부 스케줄러가 직접 관리**하는 **유저 스레드**
        - 커널 스레드를 새로 만들지 않음 → **수만 개도 가볍게 생성 가능**
        - 블로킹 시 커널 스레드를 반납하고 대기 → 고성능
        - 이건 OS 입장에선 **"보이지 않는 스레드"** → 오직 JVM 내부에서 스케줄링됨

- **단일 프로세스 시스템에 대해 설명한 후, 단점을 말해주세요.**
    - 단일 프로세스 시스템은 컴퓨터의 초기 동작 방식으로, 한 번에 하나의 프로그램만 실행되는 시스템을 의미한다.
    - 단점은, CPU 사용률이 좋지 않다는 점인데, 예를 들어 P1이 I/O 작업을 하는 동안 CPU는 놀고 있게 된다.

- **멀티프로그래밍에 대해 설명해주세요.**
    - 여러 프로그램을 메모리에 올려놓고 번갈아가며 실행시키는 개념
    - 멀티태스킹과의 차이는 비선점형이라는 점!
    - 따라서 CPU 사용 시간이 길어지면 다른 프로세스가 계속 대기하게 되는 문제점이 존재하였다.

- **멀티태스킹에 대해 설명해주세요.**
    - 하나의 시스템(운영체제)이 여러 작업(Task)을 동시에 처리하는 것처럼 보이게 하는 개념
    - 프로세스의 응답 시간을 최소화 시키는데 목적이 있다.
    - 멀티프로세스와 멀티스레드를 포함한다.

- **멀티프로세싱에 대해 설명해주세요.**
    - 둘 이상의 CPU(코어)를 사용해 여러 작업을 진짜로 동시에 수행하는 것
    - 하드웨어적 개념으로, 각 프로세스(혹은 스레드)가 각기 다른 CPU에서 병렬로 실행 가능하다.
        - 4코어 CPU에서 4개의 프로세스가 동시에 병렬 처리됨

- **멀티프로세스를 설명해주세요.**
    - 하나의 프로그램이 여러 개의 프로세스로 작업을 나누어 처리하는 구조
    - 각 프로세스는 메모리 공간을 독립적으로 사용
    - 안정성이 높지만, 프로세스 간 통신(IPC)이 복잡하고 비용이 큼
        - IPC란 운영체제 상에서 실행 중인 프로세스 간에 정보를 주고받는 메커니즘을 말한다. 이를 위해 파이프, 소켓, 메세지 큐 등 다양한 방법이 사용된다. 그런데 IPC 자체로 오버헤드가 발생한다.
    - 하나의 프로세스가 종료되어도 다른 프로세스는 독립적으로 동작 가능
        - 크롬 브라우저: 탭마다 프로세스를 분리 → 하나가 멈춰도 전체는 정상

- **멀티스레드를 설명해주세요.**
    
    하나의 프로세스 내부에서 여러 실행 흐름(스레드)이 동시에 실행되는 구조
    
    - 코드, 데이터, 힙 메모리를 공유하되, 스택과 레지스터는 독립적
    - 자원 공유가 쉬움 (공유 메모리 기반), 컨텍스트 스위칭도 가볍다
    - 하지만 하나의 스레드가 죽으면 전체 프로세스에 영향을 줄 수 있음
        - 웹 서버: 요청마다 하나의 스레드를 생성해 처리 (Tomcat)

- **멀티프로세스와 멀티스레드는 각각 어떤 작업에 적합한지 설명해주세요.**
    
    실제로 CPU를 사용하는 작업의 경우 멀티프로세스가 유리하고, I/O 등 CPU 작업이 불필요한 작업이 많은 경우 멀티스레드가 유리합니다.
    
    다중 코어를 활용한 진짜 병렬 처리 측면에서 멀티프로세스가 더 확실한 병렬성을 제공합니다. 하나의 예시로, 파이썬은 GIL이라는 전역 락 때문에, 한 순간에 하나의 스레드만 실행합니다. 즉, 멀티스레드를 써도 진짜 병렬 처리가 되지 않습니다.
    
    반면, 멀티프로세스는 각 프로세스가 독립된 GIL과 메모리 공간을 가지므로 실제로 병렬 처리가 가능합니다. 또한 동기화 비용이 적기 때문에(파일 등 외에는 공유 데이터 없음) CPU 바운드 작업에 더 유리한 것입니다.
    
    멀티스레드가 적합한 경우는 I/O 바운드 작업인 경우입니다. 이 경우 CPU를 실제로 사용하는 스레드에만 자원을 할당할 수 있기 때문에 성능의 향상이 있습니다.
    

- **멀티프로세스와 멀티스레드의 장단점을 비교해주세요.**
    - **멀티프로세스**
        - **안정성**
            - 멀티 프로세스는 각 프로세스가 독립적인 메모리 공간을 가지므로, 한 프로세스가 비정상적으로 종료되어도 다른 프로세스에 영향을 주지 않는다.
        - **프로그램 병렬성**
            - 멀티 프로세스와 여러개의 CPU 코어를 활용하여 둘의 시너지를 합쳐, 다중 CPU 시스템에서 각 프로세스를 병렬적으로 실행하여 성능을 향상 시킬 수 있다.
            - 하나의 예시로, 파이썬은 GIL이라는 전역 락 때문에, 한 순간에 하나의 스레드만 실행합니다. 즉, 멀티스레드를 써도 진짜 병렬 처리가 되지 않는다.
            - 반면, 멀티프로세스는 각 프로세스가 독립된 GIL과 메모리 공간을 가지므로 실제로 병렬 처리가 가능하다. OS 입장에서는 멀티프로세스는 완전히 독립된 실행 단위이기에, 작업을 각기 다른 CPU 코어에 분산하기 쉽다. (따라서 CPU Intensive 작업은 멀티프로세스가 유리)
        - **시스템 확장성**
            - 멀티 프로세스는 각 프로세스가 독립적이므로, 새로운 기능이나 모듈을 추가하거나 수정할때 다른 프로세스에 영향을 주지 않는다. 그래서 시스템의 규모를 쉽게 확장할 수 있다.
            - 스케일 아웃은 컴퓨터를 여러개를 말하는 것일 수도 있고, 하나의 성능 좋은 컴퓨터에 여러개의 서버 프로세스를 두는 것을 말하기도 한다. 멀티 프로세스의 상황은 후자이다. (서버 클러스터)
        - **(단점) 컨텍스트 스위칭 오버헤드**
            - 멀티 태스킹을 구성하는데 핵심 기술인 컨텍스트 스위칭 과정에서 성능 저하가 올 수 있다.
            - 프로세스를 컨텍스트 스위칭 하면, CPU는 다음 프로세스의 정보를 불러오기 위해 메모리를 검색하고, CPU 캐시 메모리를 초기화하며, 프로세스 상태를 저장하고, 불러올 데이터를 준비해야 하기 때문이다.
        - **(단점) 자원 공유 비효율성**
            - 멀티 프로세스는 각 프로세스가 독립적인 메모리 공간을 가지므로, 결과적으로 메모리 사용량이 증가하게 된다.
            - 만일 각 프로세스간에 자원 공유가 필요할 경우 프로세스 사이의 어렵고 복잡한 통신 기법인 IPC(Inter-Process Commnuication)을 사용하여야 한다.
    - **멀티스레드**
        - **가벼움**
            - 스레드는 프로세스 내에서 생성되기 때문에 스레드의 실행 환경을 설정하는 작업이 매우 간단하여 생성 및 종료가 빠르다.
            - 멀티 스레드는 스레드 간의 통신이나 자원 공유가 더욱 용이하며, 프로세스 보다 가벼워 컨텍스트 스위칭 오버헤드도 작다.
            - 따라서 멀티 프로세스 보다 응답 시간이 빠르다. (웹 서버 사용)
        - **자원 공유 효율성**
            - 멀티 스레드는 하나의 프로세스 내에서 여러 개의 스레드를 생성되기 때문에, heap 영역과 같은 공유 메모리에 대해 스레드 간에 자원을 공유가 가능하다.
        - **컨텍스트 스위칭 비용**
            - 프로세스 컨텍스트 스위칭 비용은 스위칭할 때마다 CPU 캐시에 있는 내용을 모두 초기화하고, 새로운 프로세스 정보를 CPU 캐시에 적재해야 하므로 높은 비용이 든다.
            - 반면, 스레드 컨텍스트 스위칭 비용은 스위칭할 때 스레드 간에 공유하는 자원을 제외한 스레드 정보(stack, register)만을 교체하면 되므로 프로세스 컨텍스트 스위칭 비용보다 상대적으로 낮은 것이다.
        - **(단점) 안정성 문제**
            - 하나의 스레드에서 문제가 발생하면 다른 스레드들도 영향을 받아 전체 프로그램이 종료될 수 있다.
            - 적절한 예외 처리로 극복 가능!
        - **(단점) 동기화 문제**
            - 동기화 작업은 여러 스레드 접근을 제한하는 것이기 때문에 병목 현상이 일어나 성능이 저하될 가능성이 높다.
            - 데드락 문제가 발생할 수 있다.

- **IPC의 구체적인 방법에는 무엇이 있을까요?**
    
    프로세스끼리는 독립된 메모리 공간을 가지고 있어, 메모리를 통해 바로 데이터를 주고받을 수 없습니다. 따라서 IPC(Inter Process Communication)을 이용합니다.
    
    IPC에는 공유 메모리 방식과 메세지 전달 방식이 있습니다.
    
    공유 메모리 방식은, 통신하려는 프로세스들이 공유하는 메모리 공간을 확보하고, 그 공간에 함께 접근할 수 있게 하여 데이터를 주고받는 방식입니다. 직접 메모리에 접근하므로 빠르게 데이터를 교환할 수 있다는 장점이 있지만, 공유 메모리 공간에 대한 동기화 문제를 프로세스들이 직접 책임져야 합니다.
    
    메세지 전달 방식은 커널의 시스템 콜을 통해 프로세스끼리 정보를 전달하는 방식으로, 파이프, 소켓, 메세지 큐 등이 있습니다. 공유 메모리 방식보다 속도가 느리지만, 동기화 문제를 신경쓰지 않아도 된다는 장점이 있습니다.
    
    - **파이프:** 한 방향으로만 데이터를 전달하는 통로
    - **소켓:** 프로세스 간 양방향 통신을 가능하게 해주는 통로
    - **메시지 큐:** 커널이 중간에 메시지를 보관하는 우체통 같은 구조
